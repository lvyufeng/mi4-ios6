# Experiment 470 — a stale option header, and the exec that killed `initproc`

**The boot reached `load_init_program` for the first time and then panicked about having killed the
process it was starting.** The OS console reads

    Added memory device md0/rmd0 (02000000/0D000000) at 00000000804FD000 for 0000000000002000
    BSD root: md0, major 2, minor 0
    VM_TEST_DEVICE_PAGER_TRANSPOSE: PASS
    load_init_program: attempting to load /usr/local/sbin/launchd.development
    load_init_program: failed loading /usr/local/sbin/launchd.development: errno 2
    load_init_program: attempting to load /sbin/launchd

and then stops — **with no `failed loading /sbin/launchd` line**, which 467's zeros-image run did print
(`errno 8`). The image then reports exactly one trap, in kernel mode, at the `udf` inside
`DebuggerTrapWithState` (`xnu_entry_undef_pc = 0x800364c0`, `spsr = 0x60000093`), and
`xnu_entry_panic_entered = 1`. **One entry, so there was no user-mode fault first**: the Mach-O never ran
its first instruction, and the trap is a `panic()` rather than a fault.

**The name is in the one format-string reading the trap takes.** `xnu_entry_trap_r9_fmt = 0x804b291b`
resolves to `"unexpected SIGKILL of %s %s with reason -- namespace %d code 0x%llx description %.800s"`,
which is `bsd/kern/kern_sig.c:2138` — `psignal_internal`'s `if (signum == SIGKILL && p == initproc)`
`panic_plain`. And the argument the same report carries agrees with the `else` branch that reaches it:
`xnu_entry_panic_arg1 = 0x804f49eb` is the empty string, i.e. `(p->p_csflags & CS_KILLED)` is clear,
which is what `unexpected_failure = TRUE` sets.

So the missing `failed loading` line is not a success. `kern_exec.c`'s `badtoolate` label is reached from
eight failures *after* the image has been activated and ends with `error = 0` under the comment "We can't
stop this system call at this point, so just pretend we succeeded" — so `load_init_program` prints nothing
whether the exec succeeded or failed there, and the console alone cannot tell the two apart. 471 is the
step that instrumented the difference; this step is what the console had, plus one defect.

**The defect: the option headers were one configuration out of date, and the check could not see it.**
`tools/gen_option_headers.py` writes each component's `meta_features.h` and the per-option headers
(`development.h`, `mach_assert.h`, `config_macf.h`, …) from the configuration — but in this build it was a
**hand-run prerequisite**, and only `tools/check_option_headers.py` ran. That check compares the generated
files against `conf/files`: membership and cross-component reads. It does **not** compare their *values*
against the configuration, so it passed over a header set written for another configuration.

Measured: `out/xnu_options/STAGE90_XNU/development.h` held `#define DEVELOPMENT 0` while the configuration
selects `options DEVELOPMENT` (`config/MASTER:611`) and `xnu_config/make_defines.sh STAGE90_XNU` prints
`-DDEVELOPMENT=1`. The block that turns on it —

    /* Check properties of static executables (disallowed except for development) */
    #if !(DEVELOPMENT || DEBUG)
        return (LOAD_FAILURE);
    #endif

`bsd/kern/mach_loader.c:631-636` — is inside `#if CONFIG_EMBEDDED`, which this configuration does not
select either, so **the staleness changed nothing about this run's failure**; that is what 471's
instrument measured, and it is written down here because the first reading of the log treated the
`DEVELOPMENT` mismatch as the cause and only the next device run disproved it. The header was still wrong,
and the *class* of wrongness is 440's (an input the compile depends on, generated by a step nothing runs),
so it is fixed as one: `build_xnu_arm_kernel.sh` now **generates** the option headers with
`gen_option_headers.py` and then runs the check, and the reading after the fix is
`development.h` = `#define DEVELOPMENT 1`, `out/xnu_kernel_obj/bsd_kern_kern_exec.o` carrying
`U task_importance_update_owner_info` (the call is inside `#if DEVELOPMENT || DEBUG`) — both were absent
before. The rebuilt image is byte-identical in `.text`, `__bss_start` and image size to the one before it,
which is the second, independent statement that this defect was not the frontier.

**Measured:** device run exit 0, `No errors detected`, device back on Android by itself; log
`/tmp/cancro-470-last_kmsg.txt`, 484092 bytes. Entry image `.text` 5218912, image 5437860, `.bss`
`0x8052f9c0 .. 0x805873f8` (358968 bytes), headroom 1543176, payload 8458240 bytes. The RAM disk's own
address reads back out of the registry as `xnu_live_prop_w0 = 0x804fd000` / `w1 = 0x2000`, and
`xnu_entry_stub_hit_count = 0` — the pseudo-init walk that 469 stopped inside now completes.
