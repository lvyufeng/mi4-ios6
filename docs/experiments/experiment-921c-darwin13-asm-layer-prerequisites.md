# 921c — Darwin-13's ARM assembly layer: two generators that hard-coded 4570 (2026-10-08)

After 921 the Darwin-13 kernel **compiles** (372/409, 0 failures), but it is not **linked** — and the
link is gated by a layer below the kernel: the ARM `.s` files, and the `assym.s` those `.s` files need.
Two of the generators that produce that layer had a 4570 fact written into them, and each refused
Darwin-13 with a **correct refusal that named the wrong cause**. This rung points both at the selected
tree, and the D13 assembly layer builds for the first time: **26 of 32 files assemble**, `make check`
stays 0, and 4570 is unchanged.

## The premise, twice (again)

Neither of these is a *value* that could be set by a switch; each is a **structural fact about the
tree**, read wrong because it was transcribed from 4570:

| file | 4570 says | Darwin-13 says | what followed |
|---|---|---|---|
| `tools/xnu_config/arm_asm_defines.sh` | `SLIDABLE=1` (`config/MASTER.arm:77`) — a real RELEASE option, exempted from the assembly | **no `SLIDABLE` at all** | the claim-check refused *every* D13 assembly: `exception 'SLIDABLE' is not an option of RELEASE` |
| `tools/gen_assym.sh` | `genassym.c:107` emits `DEFINITION__define__<SYM>: .ascii "<VAL>"`, read by `Makefile.template:189` | `genassym.c:110` emits `#DEFINITION#…`, read by its **own** `Makefile.template:123` | the 4570 `sed` matched nothing → `0 defines`, refused by the non-empty floor |

Both are the project's recurring class: **a fact true of 4570, false of Darwin-13**, in a tool the
build calls on every tree.

## 1. `arm_asm_defines.sh` — an exception is a claim about *a* tree's configuration

`ARM_ASM_EXCEPTIONS=(SLIDABLE)` is a *claim about the configuration* — the file even checks it at the
end ("an exception that has stopped being an exception must fail the build rather than stay on the
list"). `SLIDABLE` is `4570 config/MASTER.arm:77`; Darwin-13 has no `SLIDABLE` anywhere, so the claim
is false for D13 and the check refuses — loudly and correctly, but the answer is not to take the name
off the list (that would break 4570).

An exception is dropped for a tree that does not declare it. The list is **kept in one place** and
filtered by a grep over the tree's own `MASTER`/`MASTER.arm`:

```bash
XNU=${XNU_TREE:-$REPO_ROOT/external/xnu-4570.1.46}
if [[ -f $XNU/config/MASTER ]]; then MASTER_DIR=$XNU/config; else MASTER_DIR=$XNU/osfmk/conf; fi
TREE_EXCEPTIONS=()
for e in "${ARM_ASM_EXCEPTIONS[@]}"; do
    grep -qwE "$e" "$MASTER_DIR"/MASTER "$MASTER_DIR"/MASTER.arm 2>/dev/null && TREE_EXCEPTIONS+=("$e")
done
```

The `--exceptions` output, the filter loop and the claim-check all use `TREE_EXCEPTIONS`, so the
checker (`check_asm_config.py`, which reads the list at runtime) stays consistent with the filter.
Take the "one value, two definitions" defect and remove it: the value is still written once, and the
tree decides whether it applies.

**4570 neutrality, measured:** `--exceptions` still prints `SLIDABLE`; the 4570 RELEASE defines still
have `SLIDABLE` filtered out (count 0). The change is inert on 4570 down to the assembled output
(§Verification).

## 2. `gen_assym.sh` — the marker and the `sed` that reads it are a pair, and the pair changed

Apple's `assym.s` is generated by compiling `genassym.c` to assembly and scraping the constants out.
The scrape is not general: it depends on the exact text `genassym.c` writes. Between the trees:

- **4570** — `osfmk/arm/genassym.c:107`:
  `__asm("DEFINITION__define__" SYM ":\t .ascii \"%0\"")`, scraped by
  `osfmk/conf/Makefile.template:189`.
- **Darwin-13** — `osfmk/arm/genassym.c:110`:
  `__asm("#DEFINITION#\t.set\t" SYM ",\t%0")` / `__asm("#DEFINITION##define " SYM "\t%0")`, scraped by
  its **own** `osfmk/conf/Makefile.template:123`.

Running 4570's `sed` over D13's `genassym.s` matched zero lines; the floor (`< 100 → refuse`) caught it
— a wrong-answer refusal, not a silent empty file. The fix selects the rule by **the marker the
generated file actually contains** (`grep -q 'DEFINITION#'`), so a tree that changes the marker again
is refused here rather than producing a wrong `assym.s`. The D13 branch is the tree's own `sed`, with
**one adaptation that is a property of this harness, not of the tree**: the tree's rule reads
`genassym.o` (the marker survives as `#DEFINITION#` in a string literal), while this step reads clang's
`-S` text, where clang renders the leading `#` as the ARM comment character `@` → `@DEFINITION#`.

The three-name locore check (`ASSIST_RESET_HANDLER`, `CPU_DATA_ENTRIES`, `CPU_DATA_PADDR`) is also a
4570 contract: D13's `genassym.c` defines none of them (`grep` count 0 in D13, 1 in 4570). It is now
gated on the rule — the names are asked of 4570 only, and the `< 100` floor still guards the general
case for every tree.

**Result:** D13 `assym.s` = **142 defines** (from 252 lines, rule `darwin13`); 4570 `assym.s` =
**266 defines** (from 571 lines, rule `4570`) — its unchanged value.

## What the D13 assembly layer now does

`tools/assemble_arm_layer.sh` with the D13 knobs assembles **26 of 32** manifest `.s` files. The six
still failing are D13 dialect work for a later rung, not generator faults:

- `bcopyinout.s`, `hw_lock.s`, `locore.s`, `machine_routines_asm.s`, `traps_lo.s` — the EABI source
  translation (the `#DEFINITION#`-era tree spells some constructs the way the 4570 tree does not);
- `cswitch.s` — `patch_idle_stack.py` found no `LEXT(Idle_context)` line, so the idle-stack patch's
  semantic edit (`STAGE90_XNU_IDLE_STACK=1`, size 16384) matched **0** objects where it expects 1, and
  the script reports it rather than proceeding.

## The wall the link meets next (named, not closed)

Building the D13 **kernel** and the D13 **assembly** is necessary but not sufficient: D13's own
**object set** is missing the C++ spine. `out/xnu_kernel_obj_d13/` has **4 `iokit/` files and no
`libkern/c++/`** at all (no `OSObject`, `IOService`, `IORegistryEntry`, `OSMetaClass`), because
Darwin-13's ARM configuration disables them:

- `osfmk/conf/MASTER.arm:12` — the ARM `RELEASE` attribute list is
  `[ bsmall arm iokit mach_pe … ]` — **no `iokitcpp`, no `libkerncpp`**;
- 4570's lists **do** carry `iokitcpp`/`libkerncpp` (`config/MASTER.arm:40,44`), which is why our
  `IOKIT_KERNEL_*` / `LIBKERN_CXX_*` objects resolve on 4570 and not on D13.

Our whole platform block (`src/platform/darwin13/*.cpp`, the `MSM8974*` C++ objects) subclasses
`OSObject`/`IORegistryEntry`, so those objects' ~225–271 undefined symbols per object are **C++ IOKit**
that D13's object set does not currently supply. This is a false negative *by configuration*, not a
missing source: `iokit/conf/files` and `libkern/conf/files` list `IORegistryEntry.cpp`, `IOService.cpp`,
`OSObject.cpp` … `optional iokitcpp`/`optional libkerncpp`, and the files are on disk. Enabling them for
D13 is the next rung, and it is staged work in the untracked tree + the manifest selector — the same
shape as 918/920, one level up.

## What this does not do

It does not link the D13 image (`build_entry.sh` still selects `out/xnu_kernel_obj*` with 4570's
closure), it does not assemble the six D13 `.s` dialect files, and it does not enable D13's
`iokitcpp`/`libkerncpp`. It makes the **layer below the kernel** follow the tree, so the link rung
starts from a D13 assembly rather than a 4570 one.
