# The byte sets this project can REVERT `out/stage90/` to, recorded as hashes.
#
# WHO WRITES THIS: by hand, in the step that measured the set, and never by the build. That is the same
# rule `tool-images.txt` follows and for the same reason - a record the build writes agrees with itself
# and constrains nothing. The comparison lives in `tools/verify_revert_set.sh`, which hashes a directory
# against the lines below and refuses when a file is absent, empty, the wrong size, or the wrong bytes.
#
# WHY A REVERT SET NEEDS A RECORD AT ALL. The user's standing constraint is that the device must never
# be bricked and never hang permanently, and the mechanism behind that claim is not the watchdog - it is
# that the arm in `out/` can always be put back to one that was known to reach a specific point. That
# mechanism is a directory of files. Those files are **outside version control**: `out/` is gitignored
# and the 574 park is in `/tmp`, so the hashes below are the identity and the copies are only copies.
# Until this file existed, the identity appeared in prose in 22 documents and in no form a program could
# compare against.
#
# WHAT MAKES A SET COMPLETE, and it is not a list someone remembered. **A revert is complete when the
# gate is green on the reverted tree**, and the gate reads in TWO ways - so the set is the union of two
# derivations, not one:
#
#   A. the paths it names in its own text. `preflight_boot_check.sh` consumes nine under `$OUT`
#      (`SHA256SUMS.txt`, `stage90.bin`, `stage90-build-config.txt`, `stage90.elf`, `stage90-qcdt.img`,
#      `xnu_arm_entry.bin`, `xnu_arm_entry-config.txt`, `xnu_arm_entry.elf`,
#      `xnu_arm_entry-sources.txt`). Both spellings are needed - eight are written `$OUT/name` and one
#      (`xnu_arm_entry.elf`, in a narration path) `out/stage90/name` - so a derivation that greps one of
#      them returns a shorter list, and a shorter list is what a missing record line looks like:
#
#        grep -oE '\$OUT/[A-Za-z0-9_.-]+|out/stage90/[A-Za-z0-9_.-]+' \
#          stages/stage90/preflight_boot_check.sh | sed 's|\$OUT/||; s|out/stage90/||' | sort -u
#
#   B. **the members of the manifest it verifies.** `preflight_boot_check.sh:139` is
#      `( cd "$OUT" && sha256sum -c SHA256SUMS.txt )`, and `sha256sum -c` opens every path the manifest
#      names. That manifest is itself a member of the set, so **this half of the criterion is a property
#      of a file INSIDE the set and not of the gate's text**: no grep of the gate can return these names,
#      and the manifest's member list is build-dependent (it is generated by `build.sh:389`). Today it
#      names five - `stage90_fixture.macho`, `stage90.elf`, `stage90.bin`, `stage90.img`,
#      `stage90-qcdt.img` - of which three are already in A and **two are not**. B is therefore pinned
#      HERE, as the `manifest_members=` field of the manifest's own line, so that the criterion is closed
#      over this record rather than over the live tree: reading it out of `out/stage90/SHA256SUMS.txt`
#      would read the one file whose contents the next build changes, and it would be right today only
#      because the live and parked manifests happen to name the same five.
#
# **A nine-member set built from A alone was this record's first version, and it was wrong**, in the way
# that costs the most: reverting the nine and leaving the live `stage90.img` in place makes the restored
# manifest's own check print `stage90.img: FAILED` - the gate RED - on a record whose whole purpose is
# that a revert cannot leave the gate red. Measured, not argued: the four other members print OK, and
# `stage90_fixture.macho` is `52bc9c35…` in both arms, which is why that one is benign today and
# `stage90.img` (`28ee2c22…` live against `8274b1c4…` frozen) is not. The mechanism half of A+B, and the
# simulation of the red line, are in `tools/rehearse_revert_set.sh`, which derives BOTH halves at run
# time and refuses when the record does not cover them.
#
# The strongest check is still not a derivation at all: revert, then run the gate. Run it before
# believing any record, including this one.
#
# THE TRAP THIS FILE EXISTS TO NOT READ. Every build writes its own `SHA256SUMS.txt` with **absolute**
# paths into the tree that produced it, and a park is a copy of those files *outside* that tree. So
# `sha256sum -c SHA256SUMS.txt` run inside a park hashes `/mnt/data/mi4-ios6/out/stage90/*` - the live
# tree, which has moved on since - and prints `FAILED` for every file that changed while the parked
# bytes are all correct. A manifest of absolute paths is a record of a *location* and not of a
# *directory*: it verifies wherever you run it, and what it verifies is the path it names. It has
# already produced one wrong reading in this project (595's session, whose rehearsal mirror re-read the
# real `out/` from inside the mirror). `verify_revert_set.sh` therefore reads THIS file and never the
# target's own manifest, and it prints the absolute path of every path in a manifest it finds as a
# narration line, so the trap is stated at the moment a reader meets the directory.
#
# The park's own `SHA256SUMS.txt` is below as a member of the set, with the hash 591 recorded for it. It
# is deliberately NOT rewritten to relative paths: editing it would falsify 591's record and this one,
# and a frozen artifact is not something to tidy. The defect is recorded instead - which is why the file
# that cannot be trusted as a manifest is still pinned as bytes.
#
# ONE FILE PER LINE, space-separated key=value:
#   set=      which revert set the line belongs to; the tool verifies one set or all of them
#   sha256=   the key into the line; a changed byte anywhere refuses
#   bytes=    a second, independent field of the same bytes - a size and a hash agreeing is what turns
#             a typo in either into a reading instead of a silence
#   file=     the name as it appears in `out/stage90/` and in every park of this set
#   role=     what this file is for. A role is not inferable from a name, and a revert that omits a
#             file it did not recognise is the failure mode this field exists to prevent.
#   manifest_members=  on the line whose file= is the manifest, the member list that manifest carries,
#             comma-separated. This is the record's copy of criterion B (see below) so that B is
#             **closed over the record** instead of read out of the live tree: the manifest a revert
#             puts back is the record's own member, so its member list is a fact the record can pin, and
#             `tools/verify_revert_set.sh` refuses if any name here is not also a `file=` line of the
#             same set. Without this field a reader would have to open the target's manifest - which is
#             the one file whose contents the next build changes.
#

# wiped it - but nothing protected it either, and a run of `build.sh` or `build_entry.sh` would have
# destroyed the one unrun arm in this project whose loss cannot be undone by rebuilding. A record of the
# bytes, plus a park, is the same protection 611 gave the 574 arm, applied where the risk actually was.
#

# 690: THE CLOCK ARM - `armed-post-endticks-b12616bc`. 688 ended the run at a COUNT (the second post
# call); this one ends it at a CLOCK (an elapsed-ticks deadline) at the same site and through the same
# call. `STAGE90_XNU_POST_END_TICKS=115200000` replaces `STAGE90_XNU_POST_END_RUN=2`; the two are
# mutually exclusive, refused by `entry_trace.c` (`#error` on both set) and by `build_entry.sh`.
#
# WHY TICKS AND NOT MILLISECONDS, and where the rate comes from. 115,200,000 is 6000 ms at the 19200
# ticks/ms the payload's own device tree states - 3x the fixture's 2000 ms park (`PARK_MS` in
# `entry_ramdisk.s`), so the boundary lands inside a park and not between two. But that rate is a
# COMMENT and a device-tree claim: nothing in this project has ever measured it (grepped). So the
# switch is in the units the hardware counts - CNTVCT ticks, via `entry_counter()` - and the arm
# PUBLISHES the hardware's own statement of the rate, `CNTFRQ`, as `xnu_live_post_cntfrq`.
# `run_and_capture.sh` computes milliseconds from the log's own rate when it is present and PRINTS which
# source it used, so 6000 ms in this record is the expected reading and not an assumed one.
#
# MEASURED IN THE ELF, not inferred from the switch:
#  * `__wrap_platform_cache_idle_exit` (0x8047cad8) keeps its EIGHT-byte frame (`str r4, [sp, #-8]!` /
#    `str lr, [sp, #4]`), gives it back (`add sp, sp, #8`) and ends in a TAIL BRANCH, not a call:
#    `8047cb44: ldr r1, [r3, #24]` - `g_slot_post` 0x805100f8 + 24, the post site's own `calls` field, so
#    no new counter and no new site - then `8047cb48: b 8047b530 <entry_post_clock>`. **This frame IS the
#    slot**: the exit's `push {fp, lr}` writes *this* `sp` and its `pop {fp, pc}` reads it back, so a
#    16-byte frame moves the reading to an address that is real and quiet and wrong. The 690 build caught
#    exactly that - an inline first version of the clock came out `strd r4, [sp, #-16]!` - which is why
#    the clock is `noinline`.
#  * `entry_post_clock` (0x8047b530) takes `now` and `calls`. Its first-call path (`cmp r1, #1` / `bls`
#    at 0x8047b530/0x8047b540) reads CNTFRQ (`mrc 15, 0, r2, cr14, cr0, {0}`, 0x8047b5e4) and stores the
#    baseline: `g_post_clock_freq` 0x805a0570, `g_post_clock_t0` 0x805a0574, `g_post_clock_elapsed`
#    0x805a0578 - three `static uint32_t`, 12 bytes, which is why `.bss` grew 8 and not 12.
#  * the deadline is a `mov`/`movt` pair - `mov r3, #0xd000` / `movt r3, #0x6dd` = 0x06ddd000 =
#    115,200,000 - compared by `sub r0, r0, r2` / `cmp r0, r3` (r2 = t0) / `bcc` at 0x8047b55c-0x8047b568.
#  * `entry_seam_end_run` is at 0x8047b47c in BOTH ELFs - it did not move - while the wrapper moved from
#    0x8047c994 to 0x8047cad8 (+0x344). The ending is `bl entry_seam_end_run` at 0x8047b5b8, whose
#    IMMEDIATELY PRECEDING instruction is `bl entry_live_write` at 0x8047b5b4: the publish is the last
#    thing before the ending, *locally*, which is the clause the build checks. The stronger test - "the
#    ending is the function's last call by address" - is not a fact about the function (gcc keeps the
#    first-call branch and a second copy of the publish after the ending's block), and the build's own
#    failure text says that rather than pretending otherwise.
#  * the four live keys are in the image verbatim: `xnu_live_post_t0`, `xnu_live_post_cntfrq`,
#    `xnu_live_post_elapsed`, `xnu_live_post_end_calls`. The fourth is published on the ending path ONLY,
#    which is what makes the negative cell readable. The arm's identity is published by the seam as
#    `xnu_live_seam_post_end_ticks` (0x06ddd000) beside `xnu_live_seam_post_end_run` (0).
#
# PRE-REGISTERED HERE, BEFORE ANY PRESS, because the ending moved one call deeper and the abort records
# the call site: the ending is reached by a TAIL BRANCH out of the wrapper, so the `bl` that leaves `lr`
# for `entry_seam_end_run` is the one inside `entry_post_clock` at 0x8047b5b8. This arm's abort should
# therefore read **`xnu_live_sleh_lr=0x8047b5bc`** (the instruction after it, `sub r3, r1, #1`), where the
# 688 arm read 0x8047ca0c (after its counted `bl` at 0x8047ca08). `xnu_live_sleh_pc` stays 0x8047b488,
# the restart-reason store at `entry_seam_end_run+0xc`; and the payload's `cpu_idle` calls this wrapper at
# `8000da3c: bl 8047cad8`, so the wrapper's own return address (0x8000da40) is in `lr` up to 0x8047cb3c
# and is NOT what the abort should show. Three readings that must agree on this arm: the seam's
# `post_end_ticks`, `post_end_run=0`, and this `lr`.
#
# THE NEGATIVE CELL, and this arm's one cost. Ending on a clock makes the ending INDEPENDENT of how many
# passes happen - the first arm here whose ending counts nothing - and it moves the negative from "the
# counter did not reach N" to "the machine stopped before the clock ran out". If a pass dies where the
# first one did not, the ending never fires and this run is a no-return (exit 2), the same cost as 688's,
# paid with a power press and not with the device. And on an arm whose ending is a store that ABORTS,
# a no-return cannot be told from a hang by the log at all - the log only comes back with a return. No
# net is armed in these bytes: 666's hardware-watchdog self test is a different arm.
#

# 692: THE STORAGE ARM - `armed-storage-0da7313b`. 690 ended the run on a clock and came back with 8.008 s
# of live kernel and a measured CNTFRQ; this arm keeps **every one of that arm's switches** and adds one:
# `STAGE90_XNU_STORAGE_PROBE=1` makes `xnu_arm_boot/entry_storage.c`'s probe real. Its call is in
# `__wrap_platform_cache_idle_exit` on the wrapper's first return - the same site 690 takes its baseline
# on - immediately after `entry_note_pcx` and before the clock's block, so the probe's records precede the
# ending's last one.
#
# WHAT THE ARM DOES, AND WHY IT IS THE STORAGE LINE'S FIRST ACT ON THE DEVICE. 529/530/531/532 are the
# host-side readings of the eMMC controller: 531 read the vendor driver's two named windows
# (`hc_mem 0xf9824900`, `core_mem 0xf9824000`) and the mode bit at `CORE_HC_MODE 0x78`; 532 read the
# prerequisite under all of it - **neither window is in any table this image builds, and both are inside
# the same 1 MB section** (`0xf9824000 >> 20 == 0xf9824900 >> 20 == 0xF98`), so the arm's first act is
# ONE `entry_mmio_section(0xf9824000, 0xf9824000, ...)` and not two. The probe is 532 section 6's steps 2
# and 3: install, then read. It writes NOTHING. `xnu_live_storage_writes=0` is published as the arm's own
# safety reading, because the vendor's own probe opens with three writes (`CORE_HC_MODE <- 0`,
# `CORE_SW_RST`, `HC_MODE_EN`) and 531 section 8 gives a fourth reason to avoid the surface: writing 0 to
# `POWER_CONTROL 0x29` **is** a bus-off request.
#
# THE GATE, READ FIRST, AND IT IS THE ONE RISK THIS ARM TAKES. A load from a block whose clock is off is
# a bus wait nothing ends - the one failure this project cannot read a log out of. So before the section
# is installed the probe reads SDCC1's branch gate (`BCR 0x04C0` / `CBCR 0x04C4` at `0xFC400000`, the `+4`
# measured from 528's UART pair) and skips the six loads when `BIT(0)` is clear. That megabyte is already
# mapped in the context the wrapper runs in, proved by `entry_epilogue`'s own PS_HOLD store at
# `0xfc4ab000` on every returning run. The interlock can only fire in the safe direction.
#
# THE MEASURED ELF SHAPE. `entry_storage_probe` is at **0x8000cff8** and the wrapper's `bl` to it is at
# **0x8047cb2c** (the wrapper still opens `str r4, [sp, #-8]!`, keeps its 8-byte frame and still ends
# `ldr r1, [r3, #24]` / `b 0x8047b530 <entry_post_clock>`). In the probe's body: `movw r4,#0x4000` +
# `movt r4,#0xf982`; the section index materialized as `movw r1,#3992` (0xF98) and published twice;
# `movt r3,#0xfc40` with `ldr r1,[r3,#1216]` (BCR) and `ldr r5,[r3,#1220]` (CBCR) and `and r5,r5,#1`;
# `bl entry_mmio_section` with r0 == r1 == 0xf9824000; and exactly SIX loads off r4 -
# `[r4]`, `[r4,#44]` (0x2C), `[r4,#80]` (0x50), `[r4,#120]` (0x78), `[r4,#2304]` (=hc_mem+0x00),
# `[r4,#2368]` (=hc_mem+0x40) - with **no store to any address based on r4**. The two derived bits are
# `ubfx r1,r6,#7,#1` (`CORE_SW_RST`) and `and r1,r5,#1` (`HC_MODE_EN`).
#
# TWO DEFECTS FOUND AND REPAIRED IN THIS STEP, BOTH IN THIS LANE.
# (1) **The switch reached the record and not the file.** The first build of this arm exited 0 with
# `STAGE90_XNU_STORAGE_PROBE` added to `STUB_DEFINES` - which reaches `entry_stubs.c` and
# `entry_timebase.c` and NOT `entry_trace.c`, the file whose `#if` consumes it (`entry_trace.c` has its
# own explicit `-D` list, and the file's own `EXIT_POC_FLUSH` note says so). The record carried `=1`,
# the gate's printable key list agreed, and the disassembly of `__wrap_platform_cache_idle_exit` held no
# `bl entry_storage_probe` at all. Repaired by moving the flag onto `entry_trace.c`'s command line, and
# closed by a **new clause that reads the assembled wrapper in both directions** (the flag on requires
# exactly one call; the flag off requires none), because nothing else in the build could see the hole.
# (2) **`entry_gic.c` could not compile with the tracer off.** Its five `extern`s sat inside
# `#if STAGE90_ENTRY_GIC_TRACED`, while the no-op arm of `GIC_LIVE` still evaluates its arguments - so
# `STAGE90_ENTRY_TRACE=0`, which `build_entry.sh`'s own default sets, was a build that died at
# `entry_gic.c` with `'g_live_mmio_l1' undeclared`. Measured with the object's own command line and
# `-fsyntax-only`. Repaired by moving the declarations outside the `#if`; a declaration is not code, so
# no traced image moves a byte for it. `entry_storage.c` is written the way the repair leaves its sibling.
#
# PRE-REGISTRATION (no device was touched for any of it).
#   * `xnu_live_storage_loads` = 6 beside `xnu_live_storage_writes` = 0 - the controller answered and
#     nothing was written to it.
#   * `xnu_live_storage_map` = 1 and `_l1` a kernel-window base, `_l1_moved` - 532 section 6 step 2's
#     four refusals told apart by the numbers, not by a sentence.
#   * `xnu_live_storage_gate` = 1 opens the loads; 0 gives `_gated_out` = 1 with `_loads` = 0 (the
#     section installed and the block deliberately not touched).
#   * `xnu_live_storage_mode_bit` (`CORE_HC_MODE & 1`) and `_sw_rst` (`CORE_POWER >> 7 & 1`) - the two
#     bits 531 section 6 left open, and the first reading this project has of the state the bootloader
#     handed over. A `_mci_version` of 0 or 0xffffffff is *the block did not answer*, a reading of this
#     arm and not a failed run.
#   * The NEGATIVE CELL is a NON-RETURN (exit 2): the gate said the branch was on and the block still
#     did not answer, so the six loads never came back. It owes a power press. A mapping failure with a

#   * The ending is 690's clock, unmoved, so `xnu_live_post_end_calls` is still this arm's ending cell.

# 693: THE STORAGE ARM'S SECOND MAPPING - `armed-storage-gcc-1fc30bfe`. 692 pressed the storage probe and
# its FIRST device read died: `entry_storage_probe`'s gate read, `ldr r1,[r3,#1216]` with
# `r3 = 0xfc400000`, took a section translation fault (`fsr_frame = 0x00000005`,
# `far_frame = 0xfc4004c0`, and the panic's own `r0 = 0x80487fc8` is the pointer to the string
# `xnu_live_storage_bcr`). The published claim - that the megabyte is "already mapped ... proved by
# `entry_epilogue`'s own PS_HOLD store at `0xfc4ab000` on every returning run" - read a STORE inside a
# code path as evidence that an ADDRESS is mapped, which is the class of
# `mi4-a-device-address-can-be-right-and-undereferenceable` and whose citation is 532. **This arm is
# 692's arm with that claim replaced by the install it needed**: one more `entry_mmio_section` for the
# GATE's megabyte, taken BEFORE the gate is read, with the storage block's own install reordered to
# follow it.
#
# WHY THE REORDER IS SAFE AND WHY IT IS WORTH IT. An install is a PAGE-TABLE write and not an access to
# the medium's controller, so moving the storage block's install ahead of the gate read does not weaken
# the interlock: the gate still guards every one of the six loads. What the reorder buys is that a run
# which ends up gated out still publishes `_map`/`_slot_before`/`_desc`, so "the block was not touched"
# and "the block could not be reached" stay two different cells - the same distinction 692's own record
# asked for and could not make.
#
# THE TWO INSTALLS CANNOT COLLIDE, and that is 532 section 3.2 answered before it can fire: the GATE's
# megabyte is L1 index `0xFC4` (4036) and the storage block's is `0xF98` (3992). Both are in TTBR1's
# table (both VAs are above 0x80000000), both indices are inside 0..4095, and they are different
# indices - so `entry_section_install`'s occupied-slot refusal cannot be how either call ends.
# `xnu_live_storage_gcc_share_section` publishes that they are different, as a reading.
#
# AND THE SAME MEGABYTE IS THE RESET PATH'S. `entry_epilogue`'s two stores are at `0x0fa0065c`
# (RESTART_REASON) and `0xfc4ab000` (PS_HOLD) - two different unmapped megabytes. 684 measured the first
# faulting on 678's arm, and 692's own ninth abort shows the payload's deliberate ending faulting at
# `0x0fa0065c` as well. `0xfc4ab000` shares this arm's `0xFC4` index, so `xnu_live_storage_gcc_map = 1`
# beside a readable `_bcr` is ALSO the measurement that the PS_HOLD half of the reset path becomes
# reachable - the repair 684 named, taken here as a side effect of the gate's own mapping.
#
# THE MEASURED ELF SHAPE (the parked entry elf, read with objdump and not inferred). `entry_storage_probe`
# is at **0x8000cff8** and the wrapper's `bl` to it is unchanged at **0x8047cb2c**. The gate's base is
# `movt r6, #0xfc40` at 0x8000d084 with `mov r6, r3` (r3 is the function's zero) at 0x8000d064, so r6 is
# `0xfc400000` from 0x8000d084 on and every later read through it is that megabyte. The three index keys
# are immediately visible in the immediates: `movw r1,#0xf98` at 0x8000d090 (`_section`) and again at
# 0x8000d0a0 (`_hc_mem_section`), the constant 1 at 0x8000d0b0 (`_windows_share_section`), and

# 696: THE FIRST WRITE ARM - PARKED, NOT PRESSED. Nothing in this block is a reading: the set above
# is the arm that will be sent, and the press is the next step's act. What is recorded here is what
# was MEASURED about the set before it was parked, because two of those measurements are new.
# ================================================================================================
#
# THE WRITES ARE NOW A CHECKED PROPERTY OF THE ARTIFACT AND NOT A SENTENCE IN A COMMENT. `build_entry.sh`
# gained a **store census** for `entry_storage_probe`, run under the same `-ge 2` rung that turns the
# sequence on: it disassembles the function out of the linked `xnu_arm_entry.elf`, takes every store
# whose base is not `sp` as `<base>:<offset>` in program order, and refuses the build unless the offsets
# on one base are exactly `0x78, 0x00, 0x78, 0x78` in that order and every store on any other base is an
# offset-0 pointer write. The reason it exists is the one register this project has now written down
# twice: `POWER_CONTROL 0x29` lives in the OTHER window (`hc_mem`), and on this SoC **writing 0 to it IS
# a bus-off request** - so "no store is based on `hc_mem`" had to stop being a claim about the source and
# become a reading of the image the gate boots. It is a reading now, in both directions:
#
#   * the rung-2 image (`out/stage90/`, the set above): `base=r5 off=[120 0 120 120] other=[r2:0] bad=[]`
#     - accepted. The four are `str r4,[r5,#120]` (0x8000d344), `str r7,[r5]` (0x8000d380),
#     `str r3,[r5,#120]` (0x8000d470), `str r4,[r5,#120]` (0x8000d4b0), and the only other store in the
#     whole body is the `.bss` first-call guard `str r6,[r2]` (0x8000d068). **No store in this body is
#     based on `hc_mem` at all**, which is what makes `POWER_CONTROL 0x29` unreachable by construction
#     rather than by review.
#   * the 693 park control: `base=r2 off=[0] other=[] bad=[]` - **refused**, which is the direction a
#     check that has only ever passed cannot demonstrate. It is a real image of this project's own
#     rung-1 arm, hand-run through the clause's own text, and it is why the clause is not a tautology.
#   * and the honest wart, recorded rather than smoothed over: the base the clause compares is **modal**
#     (`stb_base` is whatever base carries the most stores), so on a one-store body the modal base is the
#     guard's register and the refusal above is a base mismatch rather than a sequence mismatch. The
#     clause never runs on a rung-1 arm - it is inside `-ge 2` - so this is a property of the *control*
#     and not of the arm; a reader who feeds it another image should read the census line and not the
#     verdict alone.
#
# AND THE CLAUSE IS PROVEN ADDITIVE BY THE STRONGEST AVAILABLE MEASUREMENT: THE IMAGE DID NOT CHANGE.
# The arm was parked, then the clause was written, then the entry image was rebuilt with the same
# seventeen switches - and **`xnu_arm_entry.bin` came back `57d55fc9…`, `xnu_arm_entry.elf` `5008170d…`,
# `stage90.bin` `33f38925…`, `stage90-qcdt.img` `9a4a8695…`: byte for byte the arm above**, with the
# payload build reporting "nothing to install". The one member that moved is the source manifest's
# `build_entry.sh` line, which is exactly what a build-script check that emits no code must do. So the
# 696 set is one arm with two source manifests, and the manifest that stands is the one whose
# `build_entry.sh` line is the LIVE file's - the same rule that refused 688 once for naming a
# `build_entry.sh` the tree no longer had.
#
# THE FIVE SOURCE FILES THIS STEP TOUCHED, and all five are inside `xnu_arm_boot/` because that
# directory is content-hashed into this very set (673): `entry_storage.c` (the sequence and its eleven
# new keys), `entry_storage.h` (the rung paragraph), `build_entry.sh` (the rung-2 `case` and the
# census), `entry_trace.c` (the seam constant, moved from `0x800462dc` to `0x800472dc` by a build
# refusal that named both numbers) and `entry_stubs.c` (the `TEX[0]` comment 695 left owed). The
# decoder repair of 695 and the reference document are **outside** that directory and are therefore not
# in this manifest - which is why the manifest is 23 files and not the whole tree.
#
# WHAT THIS SET IS NOT. It is not a press: no readiness chain, no gate, no runner and no `fastboot boot`
# has been run against it, so its cells are the 696 document's pre-registration and nothing else. It is
# not a step towards storage being usable: four stores put the controller in SDHCI mode and register no
# block device, read no sector and mount nothing. And **TWRP-to-storage stays withheld** - the user's
# condition is that the OS can already be entered, the OS is not observed booting and staying, so the
# condition is unmet and no write to storage has been made. No firer is armed.
#

# 697: THIS SET WAS PRESSED, AND THE BLOCK IS IN SDHCI MODE. Read this block before the 696 one
# above, whose pre-registration is what these sentences confirm or refute - and note that
# **nothing in the set changed**: the arm that was sent is the arm recorded above, byte for byte.
# ================================================================================================

# changed is the boot. **Nothing was written to the flash medium** - see the last paragraph.

# AND EVERY CELL THE 696 BLOCK PRE-REGISTERED, IN THE DIRECTION THAT COSTS A WRITE. All eleven keys are
# in the log, in the source's own order, with `_writes` published as a progress count (0 then 1/2/3/4)
# and `_mode_stage` beside it (1, 2, 3, 5, 6, 7, 8 - 4 is the timeout path's):
#   * `_mode_calls=1`, `_mode_refused=0`, `_mode_stage=1` - the version guard passed
#     (`_mci_version=0x10000011`), so the arm was ALLOWED to write, and its first act was not taken.
#   * `_writes=1`, `_mode_w0_read=0x00000000` - store 1 landed and `FF_CLK_SW_RST_DIS` is now CLEAR.
#   * `_writes=2`, `_mode_power_wr=0x000004C1` - `CORE_POWER <- 0x441 | CORE_SW_RST`, exactly the form

#     this is a resolution of it and not a contradiction; `_mode_timeout=1` with `_writes=2` and

#   * `_mode_pwrctl_status=0x00000000` - **the hazard 696 section 3 named and could not mitigate did not

#     previous state WAS BUS_ON, which is the case the vendor's own comment predicts it for).

#   * `_writes=4`, `_mode_w2_read=0x00002001`, **`_mode_bit_after=1`** - the final `CORE_HC_MODE` is the

#   * `_mode_stage=7`, `_mode_hci_version=0x00000000`, `_mode_capabilities=0x742dc8b2` - **the one cell
#     that came back as NEITHER branch**, and it found a wrong NAME in the arm's own source. 696
#     pre-registered "a differing pair = the mode change made visible; an identical pair = the mode bit
#     alone does not move these two words"; the reading is one word moved (`0x10 -> 0x00`) and the other
#     did not, and the vendor's own header says why: `drivers/mmc/host/sdhci.h:27` is
#     `SDHCI_DMA_ADDRESS 0x00`, `:181` `SDHCI_CAPABILITIES 0x40`, `:241` `SDHCI_HOST_VERSION 0xFE` (read
#     there by `sdhci-msm.c:2909`). So `ST_SDHCI_HCI_VERSION 0x00` and the two keys named after it read

#     the rename waits for the next edit inside `xnu_arm_boot/` because that directory is content-hashed

#   * `_mode_stage=8` - the whole sequence ran. **Not one cell of the pre-registered table is the failure
#     or the refusal cell, and the dangerous register was never touched** - not because this run checked
#     that it was not (a run cannot) but because `build_entry.sh`'s store census refuses to link a rung-2
#     image whose probe stores anywhere but `0x78/0x00/0x78/0x78` on one base, and this arm passed it.
#
# THE ENDING FIRED, THE PANIC PATH WAS TAKEN, AND 694's RECORD IS CORRECTED FROM ITS OWN PARKED CAPTURE.
# `xnu_live_post_end_calls=0x00000008` with `xnu_live_post_elapsed=0x0927730f` = **7,998.97 ms** against
# the armed 115,200,000 ticks - **1,999.0 ms** past the deadline, where 694 overshot by **11.011 ms**. The

# `panic(cpu 0 caller 0x80455668): kernel abort type 4: fault_type=0x3, fault_addr=0xfa0065c`,

# **8 s / 17 s / 24 s / 27 s** - and still unattributed, but narrowed: the log shows the panic path was

# 698: THE REGISTER-FILE CENSUS ARM - PARKED, NOT PRESSED. Nothing below is a reading of this arm on
# the device: the set above is the arm that will be sent, and the press is the next step's act. What
# is recorded here is what was MEASURED about the set before it was parked, including the one
# refusal it produced and the one mistake this step made and discarded.
# ================================================================================================
#
# WHAT THE ARM IS. It is the 696 arm plus a read-only census of the SDHCI standard register file at
# the tail of `entry_storage_probe`, under `STAGE90_XNU_STORAGE_PROBE=3`: ten reads at the widths the
# vendor's own accessors use (`STAGE90_XNU_STORAGE_PROBE` is the rung ladder's digit and the ladder is
# 0 inert / 1 read-only probe / 2 + the vendor's mode sequence / 3 + the census). The ten are
# `PRESENT_STATE 0x24` + `CARD_PRESENT`, `HOST_CONTROL 0x28`, `POWER_CONTROL 0x29`, `CLOCK_CONTROL
# 0x2C`, `SOFTWARE_RESET 0x2F`, `SLOT_INT_STATUS 0xFC`, `CAPABILITIES_1 0x44`, `MAX_CURRENT 0x48`,
# and `core_mem`'s `CORE_PWRCTL_MASK 0xE0` / `CORE_PWRCTL_CTL 0xE8` - plus `HOST_VERSION 0xFE`, the
# read 697 section 3 left owed and the reason `ST_SDHCI_HCI_VERSION 0x00` is renamed
# `ST_SDHCI_DMA_ADDRESS`. **The rung adds no store**, which is what the store census below now says
# as a reading of this artifact rather than as a claim about the source, and the ten cells are
# pre-registered in `docs/experiments/experiment-698-the-standard-register-file-read-at-its-own-widths.md`
# section 4 - the before-values the driver's own `sdhci_reset(SDHCI_RESET_ALL)` will be read against.
#
# THE REFUSAL THIS RUNG PRODUCED, AND THE DEFECT IT FOUND IN 696's CLAUSE. The first build of this
# arm did not link: the store census refused it with `entry_storage_probe stores to [r6:4 ]`, which
# are `g_storage_probed` (0x805541a4) and - the flag this very rung added - `g_storage_mode_complete`
# (0x805541a8), two adjacent `.bss` flags GCC addressed through one base register so that the second
# arrives at offset 4. **A register holding the image's own address is not a device register**, and
# 696's clause had written "not `sp`" where it meant "is a device address": the quantity it bounded
# was "stores in this body" and the quantity it existed for was "stores TO THE BLOCK". The clause is
# repaired here rather than worked around, because the next rung would have hit the same wall: each
# store's base register is now CLASSIFIED by what the body materializes it with - a `movt` high half
# >= 0xf000 is a device megabyte (0xf90../0xf98../0xfc4..), below that is this image's own
# 0x8000_0000- - and a register the body materializes with BOTH (`AMB`, GCC reuses registers: `r3`
# carries 0x8054 and 0xf982 in this very body) or with NO `movt` at all (`UNK`, a literal pool or a
# computed address) REFUSES the build, which is the direction a build check has to fail in.
#
# ITS FIRST DRAFT WAS WRONG IN THE UNSAFE DIRECTION, which is why the shapes are written down: it
# classified each store in line order, and this body materializes `r3` with `movt r3,#0xf982` at
# 0x8000d52c - AFTER a store at 0x8000d478 - so a device base whose `movt` sits after its store
# would have been read as IMG, i.e. WAIVED. The classification is collected over the whole body and
# applied at the end for that reason, and the clause now prints its own reading on success instead
# of passing silently. **This build's line reads:**
#
#   xnu_entry_698: the probe's stores, classified by base register - device [120 0 120 120 ] on r5,
#                  image [r6:0 r6:4 ], ambiguous [], unknown []
#
# and it is proven in both directions: the LIVE rung-3 image and the PRESSED 696 park both accept
# with exactly the four device stores (their images differ only in which `.bss` flags the body has),
# and SEVEN mutations of the rung-3 disassembly each refuse through the branch it was built to reach
# - offset 120 -> 124 (the offsets string), a fifth device store (the count), a store moved onto the
# IMG base `r6` (the count falling to three), a device store moved to `r3` (AMB), to `r9` (UNK), and
# a fifth store added on a second device base `r4` (the second-base branch).
#
# AND A SECOND CLAUSE OF THE SAME SHAPE IS BESIDE IT, new for this rung: the ALIGNMENT CENSUS. For
# every memory instruction in `entry_storage_probe` whose base is not `sp`, the offset must be a
# plain immediate satisfying its own access width's alignment (`ldr`/`str`/`ldrd`/`strd` -> 8,
# `ldrh`/`strh` -> 2, `ldrb`/`strb` -> 1), and a register-offset form refuses the build with the
# instruction quoted. The reason is not style: `0x29`, `0x28` and `0x2F` are byte registers and
# `0xFE` is 16-bit at a non-4-aligned offset, so a 32-bit access to any of them is an UNALIGNED
# ACCESS TO DEVICE MEMORY, which faults on ARMv7 - the same class of fault 692 measured on this
# block, reached by alignment instead of by translation. The clause makes the widths in the
# document's section 1 a property of the linked image instead of a comment. It passes on this image
# (run standalone against this very ELF before the build, and inside the build).
#
# WHAT MOVED IN THE TREE: three of the manifest's twenty-three files - `build_entry.sh` (the rung-3
# `case`, the store census's classification repair, the new alignment census), `entry_storage.c`
# (the ten reads, `st_read8`/`st_read16`, the rename, `st_standard_census`) and `entry_storage.h`
# (its rung paragraph). **`entry_trace.c` did NOT move this time**, and that is a measurement and not
# an assumption: this image's seam clause reports `STAGE90_XNU_SEAM_LR (0x800472dc` - the value 697
# had to move in `run_and_capture.sh` - unchanged, so `run_and_capture.sh`'s `EXIT_POP_LR_LITERAL`
# still matches this arm and readiness row 3 has nothing to refuse.
#
# THE DELTAS AGAINST THE PRESSED 696 ARM, all measured, not inferred:
#   * `stage90.bin` is 6,031,876 bytes in BOTH arms and 596,939 bytes differ - and **every one of
#     those bytes is inside the embedded entry blob window [494236, 6030616)**: the new entry bin
#     appears verbatim exactly once at 494236, and the payload's own code is byte-identical to the
#     pressed arm's outside that window.
#   * `stage90.elf`'s `.text` is 6,030,666 bytes in both, and the three entry bss-size immediates at
#     VA 4ac40/4ad04/4ad18 are byte-identical, because the entry image's own bss size did not change
#     (379,720 both - the new flag landed inside existing padding).
#   * the entry image itself: the elf's `.text` grew by 480 bytes (5,313,768 vs 5,313,288), the bin
#     is 5,536,380 in both because that size is padded, and the 596,939 differing bin bytes are that
#     insertion shifting everything after it around file offset 0x480000, plus every absolute address
#     that points past it (the difference is a few hundred bytes per 64 KiB block before 0x480000 and
#     54k-63k per block from 0x480000 to 0x520000).
#   * `stage90-qcdt.img` differs in 596,959 bytes: the payload's 596,939 plus the header's own
#     sha1 field at 576..595, which is the 20 bytes the gate checks.
#   * `stage90-build-config.txt` and `stage90_fixture.macho` are byte-identical to the 696 arm's.
#
# THE MISTAKE THIS STEP MADE, recorded because it is the one thing here that could have cost a
# press. The payload was first rebuilt with a plain `./build.sh`, which writes `#define
# STAGE90_XNU_ENTRY 0u` - a payload that NEVER JUMPS INTO XNU - producing a 683-byte config, a
# 6,031,820-byte bin and a 6,030,610-byte `.text`. It was caught by diffing the config against the
# 696 park before anything was sent, and the payload was rebuilt with
# `STAGE90_EXTRA_CFLAGS='-DSTAGE90_XNU_ENTRY=1' ./build.sh`, which reproduces the 682-byte config and
# the 6,030,666-byte `.text` above. The arm above is the SECOND payload build. Nothing was sent while
# the wrong one was in `out/`, and the gate would have refused it anyway
# (`preflight_boot_check.sh:1715`: `--allow-xnu-entry was passed, but this image was built with
# STAGE90_XNU_ENTRY off`) - but the refusal would have cost a readiness chain and a re-read of this
# record, which is exactly the cost the discipline exists to avoid.
#
# WHAT THIS SET IS NOT. It is not a press: no readiness chain, no gate and no `fastboot boot` has
# been run against it. It is not a step towards storage being usable: ten READS of the register file
# register no block device, read no sector and mount nothing - and the four stores it inherits from
# 696 put the controller in SDHCI mode and nothing more. **TWRP-to-storage stays withheld**: the
# user's condition is that the OS can already be entered and stays, and the OS is not observed doing
# that. No firer is armed.
#
# OWED, before this arm is anything: the readiness chain (`tools/verify_press_ready.sh`, then exactly
# one `preflight_boot_check.sh <printed flags>` and exactly one `run_and_capture.sh <printed flags>
# --expect-arm=armed-storage-census-4d66f871`), and then the press itself, which is the next step's
# act.
#

# 701: THE DRIVER'S-OWN-RESET ARM - PARKED, NOT PRESSED. Nothing below is a reading of this arm on
# the device: the set above is the arm that will be sent, and the press is the next step's act. What
# is recorded here is what was MEASURED about the set before it was parked - including the defect the
# first build of it found in a build clause's own reader, and the mutation suite that says which of
# the new census clauses fire.
# ================================================================================================
#
# WHAT THE ARM IS. It is the 698 arm plus `sdhci_reset(SDHCI_RESET_ALL)`, read out of the vendor's own
# source before it was written (`docs/experiments/experiment-701-...md`), under
# `STAGE90_XNU_STORAGE_PROBE=4`. The ladder is 0 inert / 1 the read-only probe / 2 + the vendor's mode
# sequence / 3 + the standard register file's census / 4 + the driver's own reset. Rung 4 is
# **one byte store and a bounded poll**, and everything else in `sdhci_reset` (`sdhci.c:229-279`) is
# guarded off by state a fresh host does not have: `platform_reset_enter/_exit` are members
# `sdhci_msm_ops` does not define, `host->pwr` is 0 so the `check_power_status(REQ_BUS_OFF)` at
# `:254-256` is not reached, and that is the one act in the path that could hang this device -
# `sdhci_msm_check_power_status` (`sdhci-msm.c:2179-2209`) writes no register and ends in
# `wait_for_completion(&msm_host->pwr_irq_completion)`, a wait nothing in this image would ever end.
# **The rung therefore does not emulate it**. The store is `0x01` to `SOFTWARE_RESET 0x2F` in
# `hc_mem`, the poll is `sdhci_readb(0x2F) & mask` with the driver's own 100 ms bound (1,920,000 ticks
# at this machine's 19,200,000 Hz, which 699's `_post_cntfrq` measured), and the after-values are the
# five registers the pre-registration named.
#
# **THIS IS THE FIRST STORE THIS PROJECT HAS EVER MADE THROUGH `hc_mem`.** Every device store before
# it - the four of the vendor's mode sequence - was on `core_mem`. That is why this step's build
# clause had to learn a second device base (701 section 5), and why it is the clause, and not a
# comment, that keeps the byte four offsets from this one unwritten.
#
# THE STORE CENSUS IS NOW TWO NAMED WINDOWS, AND THE BUILD SAYS SO AS A READING:
#
#   xnu_entry_698: the probe's stores, classified by base register and window - core_mem
#   [120 0 120 120 ] on r5, hc_mem [47 ](strb ) on r5, image [r6:0:str:16804 r6:4:str:16804 ],
#   ambiguous [], unknown [], unnamed-device []
#
# `core_mem` unchanged since 696 (the vendor's own order and offsets) and `hc_mem` exactly once, at
# 47 = 0x2F, as a **byte** store. **`POWER_CONTROL 0x29` is four offsets away and is what the clause
# is for**: writing 0 there IS a bus-off request on this SoC (531 section 8), so "the rung that
# writes the reset bit cannot write the bus-off bit" is a property of the linked image - the same
# shape `mi4-a-claim-in-a-comment-is-not-a-check` asks for. The two windows SHARE their `movt`
# (`0xf9824000` and `0xf9824900`), which is why the clause names the window from the *pair* of
# immediates and why a store it cannot place refuses rather than guesses.
#
# THE DEFECT THE FIRST BUILD FOUND, AND IT WAS IN THE READER. The rung-4 build failed with
# `no branch to __wrap_Idle_load_context is inside cpu_idle_exit (0x8000e504..0x8000e38c)` - an
# INVERTED range, which is impossible from `nm -n`. The cause was in `build_entry.sh`'s `sym_next`
# (and, identically, in `next_global`): the reader compared the address with `$1 == s`, and `gawk`
# compares two *numeric strings* numerically - `8000e504` parses as `8000e504` = `8e507` = **+inf**,
# so EVERY address whose digits after the `e` are all decimal digits equals every other. Measured:
# `nm -n` resolves `8000e504` to **416 lines**, and `sym_next` answered `0x8000e38c`, the symbol
# *before* `cpu_idle_exit`. The reader had been right for every arm until this one because
# `8000e2b8` and `8000e58c` do not parse (a `b` and a `c` are not digits) and because no earlier
# window sat in the `e<digits>` shape - i.e. **rung 4 did not cause the defect, it moved a symbol
# into the shape that exposes it**, and the clause that consumed the wrong range reported a false
# failure about the image. The repair is `strtonum` on both sides, unit-tested in both directions
# (old -> `0x8000e38c`, repaired -> `0x8000e58c` = `cpu_init`; and unchanged for `0x8000e19c`,
# `0x8000e3e8`), and the record of it is `docs/experiments/experiment-702-...md`. **A build failure
# is not automatically a fact about the image.**
#
# THE MUTATION SUITE, in the shape 698 section 5 used, and it is the reason to believe the clauses
# fire at all (the source was restored byte-for-byte after every mutation and the restore hashed):
#   * **M1** - a second `hc_mem` store at `POWER_CONTROL 0x29`: REFUSED, as pre-registered, with the
#     offsets read as `[47 41 ]`. This is the clause that makes the bus-off byte unreachable.
#   * **M3** - the reset compiled in on rung 3 (a store through `hc_mem` on a read-only rung):
#     REFUSED, as pre-registered ("every rung below 4 is defined as reading that window and writing
#     nothing in it").
#   * **M2, M2b, M4** - the store made 32 bits wide (`st_write8`'s own body, and a direct word store),
#     and the address aimed at a device megabyte this controller does not declare (`0xf9825000`):
#     all three REFUSED, but **by the AMB clause and not by the one each was written for** - a
#     mutated store changes GCC's register allocation, so the base register carries more than one
#     device high half and the outermost clause refuses first. **The width clause (`strb`) therefore
#     has NOT been observed to fire**, and the honest state of it is that its subject - a wider store
#     to 0x2F that still materializes the same base pair - is not a body this source produces. It is
#     recorded as owed rather than claimed as exercised.
#   * **M5** - the classifier fed its own input shape directly (a test of the reader, not of a build):
#     `CORE r11:120:str:16384`, `HC r12:47:strb:18688`, `DEVBAD r14:47:strb:0`, `UNK r8:4:str:none`,
#     `DEVLO r9:47:strb:none`, `IMG r10:0:str:none` - six records, six classes, and **the pre-701
#     classifier calls r11, r12 and r14 the same thing** (`DEV`), which is exactly why 701 added the
#     low half. `DEVBAD` is reached only here, and the difference is named.
#   * and the same awk run against the live rung-4 body reproduces the build's own census line,
#     window for window - a second derivation of the same fact.
#
# ONE HAZARD THIS STEP MEASURED AND DID NOT HAVE TO FIX. A build that FAILS leaves the mutated image
# in `out/` while `xnu_arm_entry-config.txt` still describes the last image that passed, so `out/` is
# momentarily a tree whose bin and record disagree. It is not pressable: the arm-change guard has no
# matching set, and the gate refused it with the right reading - the payload embeds the *clean*
# image's bytes while `out/` holds a different build of the same length ("what it carries at that
# length is a DIFFERENT build of the entry image rather than an absent blob"). The clean rebuild
# reproduces `00b28262...` exactly, so the build is deterministic and the residue was transient.
#
# WHAT THIS ARM DOES NOT DO. **It sets no clock** (701 section 2: `sdhci_msm_ops` replaces
# `.set_clock`, `sdhci_msm_set_clock` writes `CORE_VENDOR_SPEC 0x10C` and calls `clk_set_rate` on the
# GCC at `0xfc400000` - the megabyte 692 pressed and measured as NOT MAPPED - so the clock is a third
# block and its own step). It writes no `POWER_CONTROL`, no `CORE_PWRCTL` and no `CLOCK_CONTROL`. It
# issues no command, reads no sector, parses no partition table and mounts nothing - **one byte
# written to one register of a controller whose register file has now been read ten times**, and the
# five after-reads. **TWRP-to-storage stays withheld**: the user's condition is that the OS can
# already be entered and STAYS, and the OS is not observed doing that.
#
# OWED, before this arm is anything: the readiness chain (`tools/verify_press_ready.sh`, then exactly
# one `preflight_boot_check.sh <printed flags>` and exactly one `run_and_capture.sh <printed flags>
# --expect-arm=armed-storage-reset-00b28262`), and then the press itself, which is the next step's
# act. **No firer is armed.**
#

#
# * THE STORE IS IN THE LINKED IMAGE: `strb r4, [r6, #0x29]` at **`0x8000e26c`**, with `r6` the
#   `hc_mem` base `0xf9824900`, so the address is `0xF9824929`. **It is the first store to
#   `POWER_CONTROL 0x29` by any image in this project**, and the census clause moved with it: the
#   `hc_mem` store set is `[47 44 44 41]` (`0x2f` strb, `0x2c` strh, `0x2c` strh, `0x29` strb) where

#   `_pwr_cap` is a RE-READING and not a constant: 705 published `0x742dc8b2`, and a different word
#   here is a reading about this boot rather than a contradiction.
# * THE FIVE READINGS BESIDE IT: `_pwr_before`/`_pwr_after` (`POWER_CONTROL`, 8-bit, expected
