## What this does and does NOT say

- **DOES say:** the ~24.4 s freeze did **not** overlap the idle path. The witness's central design
  question — "was the CPU in a `wfi` that slept through the freeze, or in a long non-idle kernel
  stretch?" — is answered: **non-idle**. The freeze is spent in kernel work (fault/abort path), not in
  an idle/park (candidate (iii)/(iv) of the design's classifier, read via ABSENCE).
- **Does NOT say** which of the classifier's GIC/CPSR states held during the freeze — the sampler
  never fired, so `xnu_live_freeze_cpsr/ien/pend/ctlr` are unread. That reading needs a
  NON-idle-path witness (a sampler on the abort/fault path, or a periodic timer-IRQ probe).
- The tick still collapsed and burst: `maxd = 0x1be87a47 = 468,220,487 counts = 24.386 s` (19.2 MHz),
  `count` 135 → 477 across the burst — the 1005 shape, reproduced on a fresh boot.

## The terminal stall frame (resolved by value — `docs/1006-terminal-frame-analysis.md`)

The stall sampler's repeating frame is `pc=0x8001b48d  lr=0x8046b95c  cpsr=0x60000113` (and the
`enable_interrupts+5` / `sleh_abort+0x468` form). Resolved:

- `0x8001b32d` = `enable_interrupts+0x5` — the `push` just after the `cpsie i` (`0x8001b328`).
- `0x8001b48d` = **`ml_cause_interrupt+0xd`** — the interrupt-control path.
- `0x8046b95c` = `sleh_abort+0x468` — a **forward branch** (`ea000058  b 8046bac4`), NOT a return.
- `cpsr=0x60000113`: I-bit=(0x113>>7)&1=**0** (IRQs ENABLED), A-bit=1. The earlier "I=1" reading was an
  arithmetic error.

**The fault-return self-loop hypothesis is REFUTED**: there is no `bx lr`/`mov pc,…` at `0x8046b95c`
sending control back to `0x8001b32c`; the `bl ml_set_interrupts_enabled` has a normal return. The
pc/lr pair is a normal call on pid-1's thread freshly caught by the timer IRQ. The frame sits in
`sleh_abort`'s `vm_fault` path, consistent with 1004's WALK.

## The image-identity caveat (honest)

The capture carries no entry-image arm sha (`stage90_xnu_link_elf_sha32=0xa986a0b4` hashes the
**pool** link elf, which 1006 did not change, so it cannot discriminate 1005 from 1006; the pool
C++/asm graph is identical). **The reading above does not depend on it**: rung 512's idle witness is
present in both the 1005 and 1006 entry elves (verified by `strings`), and it is absent, so the
"never idles" conclusion holds for either image. If a positive 1006-ran test is wanted, it needs a
witness that fires on a NON-idle path.
