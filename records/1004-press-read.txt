De-slide by value (extracted `/usr/lib/dyld` from the card image: Mach-O, `__TEXT` vmaddr
0x2be00000; slide 0xFF000): the USER-mode aborts (seq 5–36) are dyld paging in **its own code and

**seq 40 `far=0x3e8dd000` is exactly the `IOS7SHREG map_slide … slide_start=0x3e8dd000` page

## The frontier: the kernel's first kernel-mode page-in of the shared-region slide page

After the 40th abort the kernel **does not crash** (no panic, death gate OPEN). Stated as
measured facts: after @:28020 (the 40th abort), the run publishes NO further abort
and NO further system call (`xnu_live_usvc` ×0 in the post-abort window), yet KEEPS RUNNING:
storage reads served, the tick climbs, the wdt pet lands. The last three syscalls before the
freeze are `xnu_live_usvc_num=0xfffffffd` ×3 = **`mach_absolute_time`**, at dyld link
`0x2be1b328` = the `bx lr` right after `svc #128` in dyld's **`_mach_absolute_time`** wrapper
(the **commpage-timebase-invalid fallback** path — the wrapper checks commpage byte
`0xffff4090` at `[r12,#8]`, finds it 0, and takes the `svc`). The wrapper is reached from
**`ImageLoader::link`** — dyld is inside the image-linking phase, snapshotting absolute time.

The interrupted frame at every late tick sample (n=9..15, pc=0x8001b1fd, `cpsr=0x60000113` SVC
mode, `sp=0xcfdbbf00`, `lr=0x8046b92c`) DECODES, by disassembly, as the CPU inside **`sleh_abort`'s
data-abort RETURN path**: `sleh_abort+0x468` (`bl ml_set_interrupts_enabled`, taken when `vm_fault`
returned success) → `ml_set_interrupts_enabled`(1) falls through into `astloop`/`enable_interrupts`
(0x8001b1ac AST check → `bl ast_taken`; 0x8001b1f8 `cpsie i`; 0x8001b1fc `push {r0,r1,r2,r7,r8,lr}`).
`pc=0x8001b1fd` is **byte 2 of that `push`** — a transient pass-through in the prologue, NOT a
spin word (`astloop`'s only backward branch is `b 0x8001b1ac` at 0x8001b1f4; nothing branches to
0x8001b1fd). The saved `I`-bit=1 is correct: `sleh` runs the fault with IRQ masked, and the
interrupted state is captured before `cpsie i`. One EARLIER sample (n=8, @:27345) is USER mode
(`cpsr=0x40000010`) at dyld `0x2be1aecc` = `_open`+0x8 (`svc #5`) — proof the sampler reads a real
user frame and that pid 1 RAN in user mode before the freeze onset (the switch is between tick 256
and 512).

**CAUTION — the frozen frame may be a MEASUREMENT artifact, not the machine's true state.** Three
facts: (i) `pc=0x8001b1fd` is ODD, while every other sampled pc is even (Thumb/ARM interworking
clears bit 0); (ii) it sits two bytes into a `push`, a pc nothing branches to; (iii) the sample's
`_nz` (frame occupancy) changes between n=10 and n=11 (0x0e→0x0f) — **the channel is still being
written while pc/sp/lr/cpsr are held**, so the six identical samples are one held frame, not six
independent confirmations. `enable_interrupts` is a HIGH-FREQUENCY pc (every `ml_set_interrupts_
enabled(1)` falls through it, and the 999/1004 hook `entry_timer_edge_probe` now sits inside it at
0x8001b208), so a sampler that catches the CPU there repeatedly may be reading a common pc, not a
dwell. **Whether the CPU is genuinely frozen here for ~24 min, versus this being the last frame the
sampler captured, is UNRESOLVED from the static image** ([[mi4-measurement-defects]]): the
conclusive test is the live advance-vs-hold plus whether `far=0x3e8dd000` is ever mapped.

## Reading (honest scope)

**1004 REFUTES the 1003 candidate (a) "the same page re-faults".** The abort set is a clean
forward walk — zero repeats at both word and page granularity — over dyld's own ~24 pages, then a
handful of kernel-mode faults. **So 1005 branch (a) (CS-validation LOOP,
`STAGE90_XNU_CS_TAINT_TRACE`) is NOT the branch the evidence selects.**

**What is proven:**
1. pid 1 executed dyld's user code (`ImageLoader::link` linking images) and faulted in its own
   pages forward, one page at a time, to the very end of the trace.
2. The LAST abort (seq 40, @:28020) is a KERNEL-mode fault on `far=0x3e8dd000` = the
   **shared-region slide page** (`map_slide` slide_start) — the first touch of the 301 MiB shared
   cache. seq 37/39 are likewise kernel-mode (stack region below dyld; dyld `__cstring`). The
   walk crosses from dyld's own image to the shared cache at the frontier.
3. After seq 40, NO more aborts and NO more syscalls; the machine keeps running (storage, ticks,
   wdt pets) to the operator's power press.

**What is NOT proven (and 1005 must settle):** whether the machine BLOCKS at, or merely STOPS
AT, the shared-cache page-in.
  (b1) **Blocked in the shared-cache page-in** — the seq-40 kernel fault's page never arrives, so
       the faulting thread sleeps in `vm_fault`'s wait; the frozen `sleh`-return frame is where
       the tick sampler lands each time. The stall is a page that never completes.
  (b2) **A frame artifact, not a live dwell** — `0x8001b1fd` is a high-frequency pc (every
       `ml_set_interrupts_enabled(1)` passes it) and its parity/position are anomalous, so the
       six identical samples may be one common pc, not evidence of a 24-min dwell. Under this
       reading the real state is invisible to 1003's sampler and 1005 needs a different witness.

**1005 = branch (b)**, but SHARPENED: the decisive instrument is not "fault rate" alone — it is
(a) **does a tick sample ever ADVANCE off 0x8001b1fd, and does the sample pc carry the E bit
correctly** (kill the artifact question — v0.1 `stage90_sample_sanitize`), and (b) **what does the
seq-40 shared-cache page-in do — does `vm_fault(0x3e8dd000)` return, and is the page ever
mapped**. That separates "blocked page-in" from "sampler artifact". A `STAGE90_XNU_FAULT_RATE`
timing (1005 draft branch (b)) is still useful to date the 40th abort, but the mapping witness is
the one that answers the frontier.

**Why it matters:** dyld paged in ~24 of its own pages and then demanded the first shared-cache
page — the wall 969 named ("launchd links a 301 MiB dyld cache"). The frontier is the kernel
handling (or failing to complete) that first shared-cache fault. Most of dyld's `ImageLoader::link`
work — and the entire shared cache — still lies beyond it.

## 1005 input

Branch **(b)**, sharpened. The frontier is the kernel's first kernel-mode page-in of the
**shared-cache slide page `0x3e8dd000`** — not a dyld self-page loop. Two instruments:
1. **Shared-cache page-in witness** — instrument `vm_fault` (or the shared-cache pager) for

   one common pc, the frontier is elsewhere.
