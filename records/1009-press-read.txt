## VERDICT — the storm is a USER-MODE WRITE PERMISSION FAULT, retried ~2 M times

**1009 names the faulting instruction and the fault status. The loop is one userspace instruction
writing to one user page that faults *permission*, over and over.** 1008's REPEAT reading holds; the
fault is not a kernel fault and not a demand walk — it is a **write to a page the user process is not
allowed to write**.

`(R) REPEAT` class **by value**, and it is decisive.

### The fault, decoded

- **`fsr = 0x0000080f`** — bit 11 (0x800) = **WnR = 1: this is a WRITE**; FS = `0xf` = `0b01111` =
  **"Permission fault, level 2"** (ARMv7 DFSR: the fault-status field is `bits[4:0]`, so FS=15, *not*
  "status 7" — the low nibble alone drops FS[4]). A **level-2 (L2 page) permission fault on a write**
  is exactly what an **APX=1 (user read-only) L2 leaf** produces. (Corrected 2026-10-14; the earlier
  read mis-decoded the FS.)
- **`abtcpsr = 0x60000030`** — mode bits `0x30 & 0x1f` = **`0x10` = USER mode**, **IRQ enabled**,
  T bit set (Thumb), Z=0 C=0 N=0. The fault is taken **in userspace**, not in the kernel.
- **`far = 0x0009a000`** — a low user VA (~630 KB), **below** the `0x80000000` split (`arm_vm_init.c:86`).
  (1008's run read the same class at `far=0x0007b000` — the *class* is constant, the *low address*
  slides run to run; both are the process's low user mappings.)
- **`pc = 0x2be8a1a0`** — the faulting instruction, in the **dyld shared cache** (`0x2be…`, the
  region 999/996 identified). A userspace store into shared-cache territory.

**So the storm is: a userspace store to user VA `0x9a000` takes a permission fault (`fsr=0x80f`,
WnR=1), and the kernel's data-abort handler RETURNS WITHOUT DISMISSING IT** — the same store
re-executes at the same address, faults again, ~2 M times, and the run freezes for 24.4 s.

## What this does and does NOT say

- **DOES say:** the storm is a **single userspace instruction** (`pc=0x2be8a1a0`, dyld shared cache)
  taking a **permission fault on a WRITE** (`fsr=0x80f`, WnR=1) to a **low user VA** (`far=0x9a000`),
  in **USER mode** (`cpsr=0x60000030`), retried ~2 M times. 1008's REPEAT holds; the fault is a
  **user write to a page it cannot write**.
- **DOES say (correction):** 1008's `far=0x7b000` and 1009's `far=0x9a000` are the SAME class — a
  low user address — **not a stable identity**; the address slides run to run. What is invariant is
  the *mode* (user), the *WnR* (write), the *fault status* (permission), and the *retry* (~2 M).
- **DOES NOT say:** *why* the page is unwritable, or *why the handler returns without dismissing*. The
  two candidate mechanisms are (i) a **`pmap`/MMU attribute bug** — a user page mapped read-only (AP
  bits) that the process must write, so every store permission-faults; or (ii) a **missing user-fault
  delivery path** — the port's `sleh_abort` user branch does not turn an unresolvable user fault into
  a signal (SIGSEGV/SIGBUS), so it returns and the store re-executes. Named next rung below.
- **No brick:** the machine is alive (`No errors detected`, watchdog fed, returned on its own).

## The reader defect fixed in this rung (`23b71d1`)

The `[ABT3]` classifier was specified (`docs/1009-design.md §5`) to decide REPEAT/SPREAD from the
**change-counts** `nfar`/`nfsr`. But those are encoded as **whole-run running maxima** (written from
abort 1, monotone) — they count changes through the walked prefix and **can never describe the
tail**. 1009's run reads `nfar=832`, `nfsr=49`, and `nfar>1` is true from the dyld walk onward, so the
first run of the reader reported **SPREAD** over a tail that is, in fact, perfectly constant. The tail
is visible in the **ladder rows' own `pcfar`/`fsr`/`abtcpsr`**; the classifier now reads those rows
at/after ordinal `0x400`, and reports `nfar`/`nfsr` as what they are. Real capture → **REPEAT**; a
synthetic tail mutation → **SPREAD** (mutation-checked). This is `[[mi4-measurement-defects]]`: **a
whole-run statistic is not a tail statistic** — the same class as 1007's `first()`-vs-`max()` defect,
from the other side.

## The next rung (1010)

Two mechanisms, one measurement each:

1. **Is the page read-only?** Publish, on the REPEAT `far`, the **L2 page-table entry** the fault
   resolved to (or the `pmap`'s view of it) — the AP/APX bits and the W/X state. If a user page the
   process must write is mapped read-only, that is the bug, and the fix is in `pmap_enter`'s attribute
   computation (`external/xnu-hd2-darwin13/xnu/osfmk/arm/pmap.c`). The **shared-cache geometry**
   (iOS7SHREG/IOS7LAB, the port's `vm_shared_region.c`) is the prime suspect: if the dyld shared cache
   is mapped read-only but a process writes a fixup into it, this is exactly `fsr=0x80f` at a `0x2be…`
   `pc` — the same region 999/996 already flagged as mis-mapped.
2. **Does the handler deliver a signal?** Read the port's `sleh_abort` **user-mode branch**
   (`external/xnu-hd2-darwin13/xnu/osfmk/arm/trap.c:510`): does an unresolvable user fault call into
   the BSD layer (`send_signal`/`psignal`) or reach a `thread_exception_return` that ends the process?
   If it returns without either, the store re-executes — the retry loop — and the fix is to add the
   delivery, not to chase the page permission.

The frontier after 1009: **a userspace store to a low user page permission-faults (WnR=1) and the
handler re-runs it ~2 M times — decide whether the page is wrongly read-only (pmap/shared-cache
mapping) or the user-fault signal path is missing (trap.c).**

## The mechanism — what is established, and what is NOT (corrected 2026-10-14)

**Established (by the capture):** the signal path is **present and complete** — `sleh_abort`'s error
branch (`trap.c:834-901`) sets `exception_type = EXC_BAD_ACCESS` (`:865`), and `:926-968` calls
`doexception` → `exception_triage` → `ux_exception` → `psignal`/SIGBUS → `task_terminate`
(`osfmk/kern/exception.c:301`, `bsd/uxkern/ux_exception.c:429-485`) — and it is **never reached**,
because the storm takes the silent retry branch (`:902-908`). That branch requires `vm_fault` to return
`KERN_SUCCESS`/`KERN_ABORTED`. So the defect is a **wrong condition, not a missing path**: `vm_fault`
reports success while the hardware keeps faulting the write.

**NOT established — an earlier draft of this file over-claimed "the storm IS the code-signing CS-taint
path".** Read by value, that is **one of two mechanisms**, and it is *not* proven by the silence:

- The demotion sites `vm_fault.c:2353/1881/1904` (`prot &= ~VM_PROT_WRITE`) fire only for a **non-write**
  `fault_type` (`(fault_type & VM_PROT_WRITE) == 0`); a write fault does **not** trip them. So if the
  PTE is entered read-only, the `prot` reaching `pmap_enter_options` (`:2565`) **already lacked
  `VM_PROT_WRITE` when it left `vm_map_lookup_locked`** — i.e. the **`vm_map_entry` denies the write**.
- That is produced *identically* whether the CS block at `vm_fault.c:2435-2485` is entered or not: with
  the block skipped (`else`, `kr = KERN_SUCCESS` at `:2494`) the same signature results. **The CS block
  is not required.**
- Where the CS block *is* entered, the success-vs-error discriminator is **`reject_page =
  cs_invalid_page()`'s return value = `CS_HARD`** (`bsd/kern/kern_proc.c:2776-2796`), **not** `cs_tainted`
  (which only gates whether the block is entered). For launchd the `CS_VALID` clear means `reject_page ==
  FALSE` ⇒ `kr = KERN_SUCCESS` (`:2478`) — a success reported even after resolving a write fault that
  cannot be honoured.

**Corrections to the earlier draft (both recorded as defects of *this* file, not of the machine):**

- `far=0x9a000` is **not** "one of launchd's own COW/data segments", and **not** the shared cache. It
  sits in the hole **below** the shared region (`0x2c000000..0x40000000`, capture `:4114`); FS=15 is a
  **level-2 permission fault** so an L2 descriptor *does* exist for it (present, user-RO). Its owner and
  PA are named **only** by 1010(A)'s descriptor.
- `pc=0x2be8a1a0` is in **`/usr/lib/dyld`'s `__TEXT`** (`0x2be00000` + slide `0x7c000`), and the store
  there computes its target from a register (`mov.w r2, sl, lsr #16` at link `0x2be0a1a0`) — consistent
  with a **stale/unrebased dyld pointer**, not with the shared cache and not with launchd's own data.

**What 1010 must read (unchanged):** on the storm fault, (A) the **L2 descriptor for `far_`** — is it
APX=1 (present, user read-only)? and (B) the **`vm_fault` return**. The **deciding third cell** is the
`vm_map_entry`'s `protection` / `needs_copy` at `:2565`: if it grants `VM_PROT_WRITE` the fault is a
pmap/prot-strip bug; if it does not, the `vm_map` genuinely denies the write and the honest fix routes
it to the exception path (SIGBUS), not a spin. Only (A)+(B)+that cell names the fix — the fix design is
in `docs/1011-design.md`, and it is **conditional on the verdict**. `docs/1010-design.md`.
