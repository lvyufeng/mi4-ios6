SUPPLEMENT (2026-10-15, host-side static verification — docs/1012-probe-keying.md)
====================================================================================
A by-value audit of THIS press's own instrument found the apex cell's PROVENANCE is
UNPROVEN, so RESULT 1 must be read with these two caveats:

 (1) ORDERING DEFECT. `__wrap_sleh_abort` calls `__real_sleh_abort(regs,type)` at
     entry_trace.c:5746 but sets the key `g_abtpte_pmpva` (via `entry_note_abt_pte(far_)`)
     at :5788 — AFTER the handler ran. The handler's `vm_fault`→`pmap_enter_options`→
     `__wrap_pmap_enter_options`→`entry_note_abt_pmp` therefore filters against the
     PREVIOUS abort's far, not the current fault. Under a fixed-VA storm the two
     coincide (the tail far is constant 0x2e000), so the rows are self-consistent —
     but the identity is not general and is not proven here.

 (2) OBJECT (pa) SMELL. All 22 apex rows carry the SAME `pa=0x8421a` (PA 0x8421a000),
     an identical physical page while the storm's fault VA is 0x2e000. That is
     consistent with the apex having observed a PAGE-TABLE-PAGE install (the pmap
     entering the L1/L2 page itself, whose own `prot` is correctly 0x3 as kernel memory),
     NOT the storm's own small page. The apex probe did not capture `fault_type` or the
     enter's own `va`/`pa` identity, so "the write reaches the apex FOR THE FAULTING VA"
     is UNPROVEN by this cell.

CONSEQUENCE: RESULT 1's verdict ((c) apex-agrees ⇒ the loss is inside/below leo_enter)
is NARROWED to "the apex cell observed SOME write-bearing enter of the SAME base table;
whether it is the storm page's enter is unproven." The (A)-walk cross-check is also
weaker than first stated: the walk is NOT globally broken — 3 of 22 rows return VALID

SUPPLEMENT 2026-10-15 (after 1013's log was read) — A BY-VALUE ERROR IN THIS RECORD

The bullet above at line ~84 says:

    "`pmap_asid_ncpus=0` (`pmap_asid.c:121`) so it takes the full `arm_tlb_flushID()` branch."

**`pmap_asid.c:121` is a STATIC INITIALIZER (`uint32_t pmap_asid_ncpus = 0;`), not the runtime
value.**  The runtime value is **1**: `pmap_asid_configure` (`pmap_asid.c:148-168`) does
`OSIncrementAtomic(&pmap_asid_ncpus)` at `:157` and prints
`All ASID/asids enabled: real_ncpus: 1, pmap_asid_ncpus: 1` — present in 25 capture files in
`out/stage90/captures/` (e.g. recovered-...-020222-last_kmsg.txt:4003), and in the 1013 log.

⇒ `pmap_flush_tlbs` takes the **ASID arm** (`pmap.c:1314-1319`):
`pmap_asid_validate_cpu(...)` then `arm_tlb_flushID_ASID(pmap->pm_asid & 0xFF)` — **TLBIASID
(c8,c7,2), an ASID-SCOPED invalidate**, NOT the full `arm_tlb_flushID()` this record asserts.

**Therefore the conclusion "⇒ so the TLB-staleness explanation is ALSO refuted by value" is NOT
supported.**  It read a stand-in and called it a value ([[mi4-stand-in-size-is-not-value]]).  The
ASID-scoped flush at `pmap.c:1319` against CONTEXTIDR written at `pmap.c:2520` (and NOT rewritten
when the same user pmap is re-dispatched, `pmap.c:2513`) is a **live, by-value, never-tested
mechanism** for the V1 cell (`LEAF_WRITABLE_STILL_FAULTS`).  `docs/1012-f1a-static.md:271-274`
got it right and named `(c2) ASID-limited flush`; this record contradicted it and the wrong
statement was load-bearing.  Full analysis: `docs/1014-design.md` §8.
