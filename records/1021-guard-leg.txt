Softlink read is COLLAPSED: the shim uses r7 (= pre-push sp, set BEFORE any further push) as the
frame pointer WITHOUT saving the old r7. Its `add r7, sp, #12` is a fixed +12 correction applied to
the shim's OWN post-push sp, and the correction exactly cancels the 3-word push it just did — so
r7 = the caller's sp, so that the shim's `[r7,#24..,#44]` reads land on the caller's 7th-8th
argument words and `[r7,#8/#12/#16/#20]` on the caller's 3rd-6th arguments. (The disassembler's
"lr"/"r9"/"ip" spellings at 0x381c662a-e are just the shim OVERWRITING those regs; the loads target
the caller's stack.) Frame map:
    [r7,#8]  = caller arg 3   [r7,#12] = arg 4    [r7,#16] = arg 5   [r7,#20] = arg 6  <-- GUARD 1
    [r7,#24] = arg 7          [r7,#28] = arg 8    [r7,#32] = arg 9
    [r7,#36] = arg 10         [r7,#40] = arg 11  <-- GUARD 2      [r7,#44] = arg 12 <-- GUARD 3

== 2. WHAT THE GUARD'S VALUES ARE ON PID 1'S CALL (from the caller, by value) ==
`__os_alloc_slow` (cache 0x3823a94c) is the ONLY in-cache caller. Its fast-trap arg slots are built
and never re-stored before `blx 0x3823e6e4`:
    0x3823a986  ldr.w r0, [sl]            ; r0 = caller's task port  (AAPCS arg 1)
    0x3823a98a  movs  r3, #0              ; r3 = mask = 0           (AAPCS arg 4)
    0x3823a98c  str   r2, [sp, #32]       ; slot 9  = 7
    0x3823a98e  mov.w r2, #4096           ; r2 = size = 0x1000      (AAPCS arg 3)
    0x3823a992  str   r1, [sp, #36]       ; slot 10 = 1
    0x3823a996  str   r1, [sp, #28]       ; slot 8  = 3
    0x3823a99a..9a8  stm sp,{0,...}        ; slots 1,2,3,4,6,7 = 0
    0x3823a9a2  str.w r8, [sp, #8]        ; slot 3 = 0x49000001 (flags)
    0x3823a9aa  blx   0x3823e6e4
So the shim receives, at guard time (assuming the shim's arg-to-slot mapping is a plain 1:1 —
see the UNMEASURED note below):
    arg 6  [sp+20] = slot 6 = 0             -> guard leg 1 (==0)  PASSES
    arg 11 [sp+40] = slot 11 = 0x1000       -> guard leg 2 (==7)  FAILS
    arg 12 [sp+44] = slot 12 = 0            -> guard leg 3 (==1)  FAILS
VERDICT BY VALUE: on this call the guard does NOT pass, so the shim takes the SLOW leg — `bl
0x381c7f74` (MIG demux), and then, unless the GOT hook is null, `blx r6`. **That is leg (b), not (a).**
This is a static read; the run that would confirm it live was not recorded. Reasonably robust: guard
leg 2's slot is a HARD-CODED 0x1000 (size), and the only value leg 2 accepts is 7, a size no page
allocation asks for. (The one soft spot is whether "arg N" == "caller slot N"; the initial 6 AAPCS
args are unpadded, and the shim's three guard loads use three DIFFERENT offsets — 20, 40, 44 —
rather than the 20/32/36 a plain slot-N reading predicts. That discrepancy is the residual.)

== 5. THE OBSERVABLES, AND WHAT THE TWO CAPTURES SHOW ==
(a) would produce: a `0xfffffff1` (-15) usvc record and a panic/`swi_mach_error`/`doexception`.
    PRESENT? NO. Both captures: `fffffff1` occurs 0 times; `panic|doexception|EXC_BAD` 0 hits.
    The 1018/1019/1020 captures across all D13 runs show 0 panics.
(b) would produce: NO -15 usvc (the MIG demux issues no `svc` — its body 0x381c7f74.. issues only
    `bl 0x381c5cc0`/`blx`/`mvn.w`, no `svc`), and the call's result via the runtime hook; the udf
    frontier at `__os_alloc_slow+0x108` if the map returns non-success.
    PRESENT? CONSISTENT, but not decisive. The usvc trace shows the LAST recorded user SVC is -3
    (`0xfffffffd`, the timebase trap) with `usvc_pid=0x1`, and NEVER -15. But the usvc window is
    capped (USVC_FULL_N = 64, src/entry/entry_stubs.c:7313) and the last -3 record sits on the last
    full-field row; the udf loop (8,183 records in 1018, via the DIRECT channel) is EXACTLY the
    region the cap is designed to starve. So "no -15 at the tail" is evidence that -15 was not the
    last thing, not proof it never happened — it is the 1018 CAP CAVEAT, not a clean reading.
    The 1018 capture's `xnu_live_undef_*` (64 rows, seq 1..0x1ff7, all `user=0x1 spsr=0x20000030
    pc=0x39cdfa54`) proves the udf frontier WAS reached and looped; 1017 named it `__os_alloc_slow`.
    So the frontier is downstream of `__os_alloc_slow`'s mach_vm_map sites — the map ran and either
    returned non-success or the udf is reached on the retry path. Neither says WHICH shim leg ran.

== 6. VERDICT ==
  * Leg (a) — fast-trap `blx 0x381c5960` — is FALSIFIED for the 1018 and 1020 runs: it is
    incompatible with the observed no-panic + no-(-15) (a -15 svc would kern_invalid->panic). It is
    ALSO refuted statically: the caller's guard field for the "arg 11 == 7" test is size = 0x1000,
    so the guard cannot pass on a page-size mach_vm_map. **residual:** whether "arg 11" is
    [r7,#40] given the shim's non-uniform offset pattern.
  * Leg (b) — guard fails -> `bl 0x381c7f74` (MIG demux) and/or `blx r6` (hook at 0x39f38086;
    note the shim's own GOT slot is 0x39f38096 — 1019 §3's "0x39f38086" is the wrong word by 16 B,
    which changes nothing in the disasm). **This is the leg the evidence points to.** Not proven live.
  * ALTERNATIVE not excluded: the udf frontier was reached before any `_mach_vm_map` shim ran at all
    (1019-osalloc-extract §3: TWO call sites, 0x3823a9aa and 0x3823aa1e, both `blx` the SAME stub).
