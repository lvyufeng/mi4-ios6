--- §1b. THE ARITHMETIC, EXPLICIT (this is the correction) ---
The OLD §1 said the `add r7, sp, #12` at 0x381c661a makes r7 equal the caller's incoming sp. That is
WRONG: the `add` executes AFTER `push {r4,r5,r6,r7,lr}`, so its `sp` operand is the POST-push sp.
Step by step, with caller_sp = the sp on entry to the shim (i.e. just before the shim's push; the
caller's own `blx` does not change sp, so caller_sp = the caller's sp at the blx):

    on entry  : sp = caller_sp
    after push {r4,r5,r6,r7,lr}   (5 regs = 20 B): sp = caller_sp - 20
    add r7, sp, #12               : r7 = (caller_sp - 20) + 12 = caller_sp - 8
    after stmdb sp!,{r8,sl,fp}    (3 regs = 12 B): sp = caller_sp - 32   (r7 unchanged)
    after sub sp, #48             : sp = caller_sp - 80                 (r7 unchanged)
    =>  r7 = caller_sp - 8  (constant for the whole body)

So the TRUE K is -8. The old claim cancelled the wrong push: the author subtracted the 3-word
`stmdb {r8,sl,fp}` (which happens AFTER the add and cannot affect it) instead of the 5-word push
that precedes it. The `add r7, sp, #12` corrects for the FIRST push only: 20 B saved, 8 B of
{r4,r5,r6,r7,lr} at caller_sp-20..caller_sp-8 reserved, and r7 is pointed 12 B above the post-push
sp — i.e. at caller_sp-8, the classic pre-ARMv6 frame-pointer point — NOT at caller_sp.
Independent corroboration BY VALUE (a second function with the SAME prologue, 0x381c66ec):
    0x381c66ec  b5f0  push {r4,r5,r6,r7,lr}
    0x381c66ee  af03  add  r7, sp, #12     ; identical idiom, r7 = caller_sp - 8
and the shim's own epilogue mirrors it: `add sp,#48` then `ldmia.w sp!,{r8,sl,fp}` then
`pop {r4,r5,r6,r7,pc}` — it restores sp from r7-independent bookkeeping, consistent with r7 never
having been the caller's sp.

--- §1c. THE CORRECTED GUARD-SLOT MAPPING ---
With r7 = caller_sp - 8, the shim's loads land on these caller stack words (word n at caller_sp+4n):
    [r7,#8]  = caller_sp+0   = word 1      [r7,#12] = caller_sp+4   = word 2
    [r7,#16] = caller_sp+8   = word 3      [r7,#20] = caller_sp+12  = word 4  <-- GUARD 1
    [r7,#24] = caller_sp+16  = word 5      [r7,#28] = caller_sp+20  = word 6
    [r7,#32] = caller_sp+24  = word 7
    [r7,#36] = caller_sp+28  = word 8      [r7,#40] = caller_sp+32  = word 9  <-- GUARD 2
    [r7,#44] = caller_sp+36  = word 10     <-- GUARD 3
So the old §1's "caller slots 6, 11, 12" is WRONG; under K = -8 the guard reads caller **words
4, 9 and 10** (caller_sp+12, +32, +36). Note the residue the old §1 flagged (offsets 20/40/44 not
being the 20/32/36 a "slot-N" reading predicts) DISSOLVES under the corrected frame: the guard
loads are just the shim's own [r7,#20/#40/#44], and r7 is 8 B below caller_sp.

--- §2b. THE blx TARGET IS A GOT STUB, NOT THE SHIM DIRECTLY (re-measured) ---
The `blx 0x3823e6e4` is NOT a direct call to 0x381c6618. 0x3823e6e4 is an ARM veneer:
    0x3823e6e4  e59fc004  ldr   ip, [pc, #4]     ; ip = *(0x3823e6f0) = 0x01d00b8c
    0x3823e6e8  e08fc00c  add   ip, pc, ip       ; pc(Thumb-checked)=0x3823e6ec; ip = 0x3823e6f0+0x01d00b8c
    0x3823e6ec  e59cf000  ldr   pc, [ip]         ; ip = 0x39f3f27c ; pc = *(ip)
    0x3823e6f0  01d00b8c  (literal)
So the callee is read from GOT slot **0x39f3f27c**, whose static value is **0x00000000** (read by
value). Consequence: the shim body at 0x381c6618 is CALLED ONLY IF the runtime fixer writes that
slot; the static cache does not name it. (Corollary: the earlier "shim GOT slot 0x39f38096" in old
§2/§5 also decodes wrong — the shim's own hook load resolves to GOT base 0x39f38088, and 0x39f38096
reads 0x6619381c, a misaligned halfword, not a pointer.) This does not change the guard arithmetic,
but it is why item (a)-vs-(b) stays inference rather than a proven call graph.
