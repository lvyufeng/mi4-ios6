THE FLAG DIFF (exact)
---------------------
tools/build_xnu_arm_kernel.sh, CC_ARGS/CXX_ARGS at the FP position:
  OFF (STAGE90_XNU_GENERAL_REGS=0, the default):  -mfpu=neon-vfpv4 -mfloat-abi=softfp
  ON  (STAGE90_XNU_GENERAL_REGS=1):               -msoft-float
ON is `-msoft-float` ALONE.  `-mfpu=neon-vfpv4` is NOT kept beside it.

WHY `-mfpu` IS DROPPED (a self-falsification, recorded because it nearly shipped)
--------------------------------------------------------------------------------
The first version kept `-msoft-float -mfpu=neon-vfpv4`, justified by the claim that
`-mfpu` lowers `mrc p10,7,%0,c8,c0,0` (proc_reg.h's cp10 move) to a plain `mrc`
instead of `vmrs`.  MEASURED FALSIFIED: that `mrc p10,7` lowers to `vmrs`/`vmsr`
under EVERY flag set tried -- `-mfpu=neon-vfpv4 -mfloat-abi=softfp`, `-msoft-float`,
`-msoft-float -mfpu=neon-vfpv4`, `-mfloat-abi=soft`, `-msoft-float -mfpu=vfpv3`.
So `-mfpu` is inert for codegen with `-msoft-float`; keeping it would leave a flag
that READS as "NEON is on" beside the switch that says it is off
([[mi4-off-option-two-spellings]]).

OFF-IDENTITY
------------
1. The resolve + FP_FLAGS choice is the FIRST thing after argument parsing in
   tools/build_xnu_arm_kernel.sh -- above every mkdir/rm/generator/compile.
2. `--print-flags` is a side-effect-free mode that prints the resolved fp flag list
   and the pool census the by-value clause is read against, then exits.
3. OFF is a 2-element `FP_FLAGS=(-mfpu=neon-vfpv4 -mfloat-abi=softfp)`; expanded at
   the FP position of both arrays, so the OFF argv is word-for-word today's.
4. Two `case` statements beside the arrays assert the COMPILED arrays carry the
   resolved spelling (and that OFF does NOT carry `-msoft-float`), exit 3 on mismatch.

INCIDENT -- `--print-flags` DESTROYED THE 705-OBJECT POOL (once)
----------------------------------------------------------------
The first placement of the resolve/print block was BESIDE the flag arrays, ~1000
lines below `rm -f "$OUT"/*.o`.  A `--print-flags` invocation therefore truncated
the D13 pool (705 objects) and exited.  It was restored by re-running
scripts/build_1020b.sh, which reproduced armed-d13-b5093f00 byte-identical to the
park (all 13 record members matched).  Fix (already in this tree): the block is now
above every side effect.  This is the [[mi4-measurement-defects]] shape -- a
read-only-looking mode with a destructive side effect.

LATENT TRAP -- `proc_reg.h`'s `mrc p10,7` inline asm (does not fire today)
-------------------------------------------------------------------------
`osfmk/arm/proc_reg.h:466-477` spells `mrc/mcr p10,7,...` inline asm (fpexc/fpscr/
fpsid/mvfr0/1/fpinst).  MEASURED: that shape lowers to `vmrs`/`vmsr` under EVERY
flag set INCLUDING `-msoft-float` alone (the lowering is flag-independent, so the
switch cannot introduce it), and `check_d13_no_neon.py` classifies `vmrs`/`vmsr`
as FP (VFP_MNEMONICS).  So IF a pool object ever instantiates those inline
functions, the ON clause (`--pool --expect none`) would REFUSE a correct arm.
It does not fire today: all 705 objects disassembled => ZERO `vmrs`/`vmsr` in the
pool.  A future pool source that reads fpexc/fpscr here must be checked against
this, or the ON census will refuse.
