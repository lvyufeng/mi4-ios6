3. THE WIRE REPORT'S CLAIM (a) IS FALSE — `&address` IS 64 BITS, NOT 4
=================================================================================================
Claim: "`copyin(regs[1], &address64, sizeof(uint64_t)=8)` spans frame slots 1 AND 2 ... so
address64 = (size<<32)|addr and the :224 guard (address64>>32) rejects."

FALSE. Slots 1 and 2 are NOT contiguous memory. Slot 1 is a POINTER (&address); slot 2 is the integer
`size`. The wrapper body proves they are the same object: at 0x381c6622 `mov sl, r1` saves the pointer
verbatim; at 0x381c6652 `mov r1, sl` puts the same pointer back in r1 for the thunk; at 0x381c6654
`ldr r2, [sp,#44]` loads `size` from the wrapper's STACK into r2. So at the svc, r1 = &address and
r2 = size are two INDEPENDENT values, and `copyin(r1, ..., 8)` reads the 8 bytes of the address object
the caller allocated — NOT the pair (r1, r2). The report's claim requires copyin to read the frame's
registers as adjacent memory, which is not what copyin does.

The 64-bit address object is measured: the caller stores {0x1000, 0} at [sp,#40] and [sp,#44]
(§1: str r0,[sp,#40] @a980; str r5,[sp,#44] @a97a), and r1 = `add r1,sp,#40` @a998. A 64-bit in/out
address variable, exactly the `mach_vm_offset_t *address` parameter
(mach_traps.h:173-177, "mach_vm_offset_t *address"). The library matches the ABI by source:
libsyscall/mach/mach_vm.c:157-177 passes `mach_vm_address_t *address`, and its fast-trap condition
(object==NULL && max_protection==VM_PROT_ALL && inheritance==VM_INHERIT_DEFAULT) holds here.

Consequence: `address64 = 0x0000000000001000`, so `(address64>>32) == 0`, and the :224 guard does NOT
fire. regs[3]=0 and regs[5]=0 also hold. **The :224 guard PASSES** — it does NOT return
KERN_INVALID_ARGUMENT. The report's central prediction is falsified by its own premise.

(i) answered: `copyin(regs[1],&address64,8)` is CORRECT; 4 bytes would be WRONG.

5. CROSS-CHECK AGAINST UPSTREAM — THE HANDLER IS APPLE'S OWN SEMANTICS
=================================================================================================
This is the tiebreaker the brief asks for, and it lands for the DESIGN doc, not the wire report.

 * The device client's stub is BYTE-IDENTICAL to Apple's `_kernel_trap_9`/`_kernel_trap_8` expansion
   (syscall_sw.h:78-79, `__BIGGEST_ALIGNMENT__ > 4` armv7k branch): `push {r4,r5,r6,r8};
   ldm ip,{r4,r5,r6,r8}`. The register set {r4,r5,r6,r8} — including r8 — is Apple's, and it is
   loaded from the STACK, so r8 is the 8th stack word, not the wrapper's live r8.
 * Apple's row (syscall_sw.c:120) is `MACH_TRAP(_kernelrpc_mach_vm_map_trap, 6, 8, munge_wwllww)`,
   and the munger `munge_wwllww` -> `munge_wwlll` (bsd/dev/arm/munge.c:211-232) in DIRECTED style is
   `marshal_no_pad(regs, args, 8)`, whose layout is r0..r6 (7 words) then `ss->r[8]` (:88-90). Apple's
   own munger therefore maps wire word #8 to **r8** and its `wwllww` type string names the LAST of
   those 8 words `cur_protection`. So Apple's wire is
     {target, addr, size_lo, size_hi, mask_lo, mask_hi, flags, pad, cur_protection}
   and on the 32-bit ABIs (armv7, and any build where the C-ABI fast path is taken) addr/size/mask
   are 32-bit and PAD_ARG_ pads nothing: the struct is 8 packed words, last = cur_protection.
 * This tree's hd2 handler (mach_kernelrpc.c:208-247) reproduces that mapping literally, and its
   `regs[N]` corresponds to Apple's wire word N because the arm dispatcher hands it the raw saved
   frame (traps_lo.s:206-214 loads only the fn ptr and `mov r0,r8`; argc is unused on arm). The hd2
   row's argc=8 (syscall_sw.c:127) matches Apple's u32_arg_words=8.
 * The device's actual runtime wire is the 32-bit collapsed form {r0..r6, r8} (SP values 0x1000/0/3),
   NOT the armv7k 64-bit form. That is fine: this tree's `mach_vm_offset_t`/`mach_vm_size_t` are
   uint32_t ("We target iOS 4.3 for compatibility", mach/arm/vm_types.h:107-109), i.e. the C-ABI
   fast path's shape — which is why the handler's `mach_vm_map(...,&address32, regs[2], regs[4],
   regs[6], ..., regs[8], VM_PROT_ALL, ...)` reads exactly those slots.

THE TIEBREAKER, STATED: the device runs Apple's OWN handler for trap -15 (stock iOS 7), and Apple's
handler reads the 8th wire word as `cur_protection` (munge_wwllww's last 'w'). Therefore the client
MUST populate that word with a protection — and it does (3). The wire report's "regs[8] is the task
port" would mean every stock iOS 7 fast-path mach_vm_map passed a port name as a vm_prot_t, which is
absurd. The report is wrong; the design doc is right.
