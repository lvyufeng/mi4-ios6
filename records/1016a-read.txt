## 2. THE TRAP THIS READ HAD TO SURVIVE — the slide, not progress

The usvc ladder's terminal row is `num = -3` (mach_absolute_time) at `pc = 0x2beef328`, and 999/1003's
frozen triple is `num = -3` at `pc = 0x2be97328`. Those pcs differ by **`0x58000`** — which is NOT
progress: the two runs are the **same link address under two DIFFERENT dyld slides**.

  - **This run's dyld exe slide = `0xd4000`**: `xnu_live_entrypt_entry = 0x2bed5028` (this capture)
    minus `__dyld_start`'s **link** vmaddr `0x2be01028` (the LC_UNIXTHREAD entry, `records/1003 §6`).
  - **1003's dyld slide = `0x7c000`** (`records/1003-stall-forensics-preliminary.txt` §6).
  - `0x2bed5028 - 0x2be7d028 = 0x58000` is the **difference between the two runs' slides**
    (`0xd4000 - 0x7c000`), and it happens to equal the raw pc difference `0x2beef328 - 0x2be97328`.
  - De-sliding each by its OWN run's slide gives the **same link address**:
    `0x2beef328 - 0xd4000 = 0x2be1b328` **and** `0x2be97328 - 0x7c000 = 0x2be1b328` = `_mach_absolute_time+0x68`.

  ⚠ **CORRECTION (this file, 2026-10-15, from `docs/1017-timebase-poll-terminus.md` §2):** an earlier
  wording of this section called `0x58000` "the dyld slide delta of this run". That is **wrong**: the
  run's slide is `0xd4000`; `0x58000` is the **two-run slide difference**. The **conclusion is
  unchanged and now better grounded** — `0x2beef328` and `0x2be97328` ARE the same link address
  (`_mach_absolute_time+0x68`) at two different slides, verified by de-sliding each by its own run's
  slide. Read naively as a `_pc` change this looks like A-PROGRESS; read BY VALUE it is a
  **rebased identity** — a measurement artefact, the class this project keeps paying for
  ([[mi4-measurement-defects]]). **No progress may be claimed from the `_pc` difference.**

## 4. THE REAL WITNESS — the stall sampler: pid 1 is SPINNING IN THE SHARED CACHE, IN USER MODE

The capture carries a SECOND, independent instrument the 1015b checker does not read: the 1003 stall
sampler (`xnu_live_stall_*`), gated on the tick's own powers-of-two ladder
(`pe_msm8974.c:523-529`), 15 samples spanning ticks 1…16384 of the 19200-tick run.

  sample   pc            cpsr        mode        sp            lr
  n=1..7   0x8001cd5d … 0x60000113  SVC/kernel  (kernel sps)  kernel
  n=8      0x2bef0420    0x00000010  USR/ARM      0x2bd298c8  0x2bed906d
  n=9,10   0x8001cd5d    0x60000113  SVC/kernel
  n=11..15 **0x3b04aa54** **0x20000030** **USR/Thumb** **0x2bd2b400** **0x00000007**

  `cpsr & 0x1f = 0x10` = **User mode**; bit5 set = **Thumb**. Per the sampler's own reading rule
  (`entry_stubs.c:4607-4623`): *"the sampled pcs are all the user pc AND IDENTICAL => pid 1 is wedged
  at one user instruction"* — a **tight user-space loop**. Five consecutive samples across a doubling
  span all read the SAME pc ⇒ **pid 1 is SPINNING**, not asleep, not in the kernel.

  **`0x3b04aa54` is inside the DYLD SHARED CACHE.** The mapping geometry is in the same capture
  (`IOS7LAB cache mapping` :4105-4108):

    mapping 0  va=0x2ee10000  size=0x0c266000  => [0x2ee10000, 0x3b076000)
    mapping 1  va=0x3b078000  size=0x01ce0000
    ...
  and the shared REGION is `0x2c000000..0x40000000` (:4098). `0x3b04aa54 ∈ [0x2ee10000,0x3b076000)`
  ⇒ **mapping 0 = the dyld shared cache.**

  ⚠ NULL CONTROL for this identification: `0x3b01f800` also occurs once in the capture

  `xnu_live_stall_pc` reads `0x3b04aa54` (x5). The identification rests on the stall sampler's pc,

## 5. WHAT MOVED, AND WHAT DID NOT

**MOVED (the qualitative change the 1015b fix bought).**

  - 999/1003: pid 1 made ~22 SVCs, then **ZERO further user syscalls for ~23 min** while the kernel
    ran. The stall samples of that era sat in the KERNEL (`enable_interrupts+0x5`, SVC mode) —
    `records/1008-press-read.txt:86`, `records/1009-press-read.txt:65`.
  - 1016-A: pid 1 makes **[64,127] SVCs** and is caught **executing shared-cache code in USER mode**.
    The CPU is no longer in a kernel abort path at the stall — it is **running the shared cache**.

  This is the first capture in the 999→1016 line in which the interrupted pid-1 frame at the frontier
  is a **user pc inside the shared cache**. 999 concluded "dyld mapped the shared cache; the run
  reached user mode" — but never *executed* there. 1016-A does.

**DID NOT MOVE (stated plainly, per the brief — this is not a victory lap).**

  1. **The terminal user syscall is still the `-3` timebase poll** (`mach_absolute_time`) — the same
     call 999/1003 froze on, at the same link address (§2). The 64+ SVCs are dominated by it
     (`num=0xfffffffd` rows at n=0x14..0x40).
  2. **The ~24.4 s interrupt freeze PERSISTS.** `xnu_live_tick_sum_maxd = 0x1be9f52b` =
     468,237,613 / 19.2 MHz = **24.39 s** — the same magnitude `records/1005-press-read.txt` measured.
  3. **A long kernel abort span persists**: `xnu_live_abt_maxcall = 0x1571b974` = 359,774,580 /
     19.2 MHz = **18.74 s spent INSIDE ONE `sleh_abort` invocation** (`call = entry_counter()-t0`,
     `entry_trace.c:5849`). That the per-invocation abort ordinal `_pcn` only reached 512 while one
     invocation ran 18.74 s says the residual is a NESTED path, not the old flat retry.
  4. **`cs_invalid_page` tolerance is unchanged** (1003, settled).

  - The **stall sampler** (§4) is the DECISIVE instrument, and it is a measurement neither 999 nor
    1003's design anticipated: it places pid 1's frame in the **dyld shared cache, USER mode, Thumb,
    identical pc x5** = a **user-space spin**.

    spin inside the dyld shared cache"*. A **new, named wall** at `pc = 0x3b04aa54`.
  - ⇒ The 1010–1015 single-address retry storm was a **SYMPTOM**, and evicting it (1015b) let pid 1
    reach and *execute* its own shared-cache code.

  **THE NEXT RUNG (1017)** must therefore be a **SHARED-CACHE-EXECUTION** rung, not another pmap read:
  identify the instruction at `0x3b04aa54` (its offset within mapping 0 is `0x3b04aa54 - 0x2ee10000 =

  store (a lock stepping on itself), a bounded-but-huge countdown, or a compare that never satisfies
