3. HARD #1 — `_wwnoproof=1` is a PROBE DEFECT, contradicted by the row's own cells
================================================================================
Every tail apex row carries `wwnoproof=1`, which the design reads as "the pmap's own `pm_l1_phys` is NOT the
base the live TTBR0 walks". But the SAME rows carry the 1012 apex cells:

    pmppmap=0x81a86000   pmpttbr=0x81a8605b   pmpprot=0x03

`pmppmap (=pm_l1_phys, read BEFORE the enter) & 0xFFFFFF00 == 0x81a86000 == pmpttbr & 0xFFFFFF00` — the pmap
table EQUALS the live TTBR0 base, which is 1012's own identity cell. And the tail flush rows independently read
`wfttb == wflive == 0x81a86000`. So the row's OWN evidence says `pm_l1_phys` IS the live table, while
`_wwnoproof` says it is not. **The two cells disagree and the pmp/flush cells are the corroborated ones.**

Cause (by value): `entry_note_abt_wleaf` (`src/entry/entry_stubs.c:2928`) re-reads
`pm_l1_phys = *(uint32_t*)pmap` AFTER `__real_pmap_enter_options` — deliberately, for the pmap_expand hazard.
`entry_note_abt_pmp` reads it BEFORE (the `__wrap` local). If `pmap_expand_ttb` fires inside the enter the two
differ; the `proof` comparison `entry_ttbr_base(pm_l1_phys, n) == entry_ttbr_base(ttbr, n)` then fails on the
NEW table. The pmp cell preserved the PRE-enter value and matches TTBR0. **This is the documented
post-call-read hazard reproducing itself as a false negative** — the cell is a NULL CONTROL outcome, and the
checker correctly refuses to pair across it. It is REPORTED, not concluded from (design §3 V4).

Consequence: the leaf PAIRING is still valid, because W-WALK read the leaf through the LIVE TTBR0
(`wktb=0x81a8605b`) — the ground-truth walk does not depend on the apex provenance gate at all.
