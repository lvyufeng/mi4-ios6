- **537 reads**, `rd_ordinal` 0x1 (@:6140) .. **0x219=537** (@:28906); `rd_err=0`,

- **Linear?** Within a run, yes: 512-byte steps (lba+1). But the whole 537 are NOT one
  monotonic sweep: 17 non-increasing pairs = run boundaries. The runs jump around
  (…0x4229xx, then 0x412c38+, 0x422ae8+, then the final run). The **last run is a perfect
  linear sweep**: 0x4a3810 (@:28852 region) .. **0x4a3842, 51 sectors, +1 each**.

  (only the terminal pet/tick stanza and the final SVC trio). So the kernel is **not** paging
  during pid 1's silent tail.

Interpretation. Paging DID interleave with the user SVCs (187 reads inside the usvc window,
roughly one 512 B read per ~10 KV lines), and the last read (@:28906) fires just BEFORE the
final 4 SVCs (n=19/20/21/22 @:28955+). After that there is nothing. This **argues against**
"pid 1 asleep waiting on a page-in the kernel is still serving": the kernel serves no page-ins in
the tail. The last activity is user-side (the mach_absolute_time trio), then silence.

## 5. THE TWO HYPOTHESES, PRE-COMMITTED

The 1003 instrument samples the INTERRUPTED pid-1 frame per tick: keys `xnu_live_stall_n/_t/_pc/
_cpsr/_sp/_lr/_nz`. The MODE is in `_cpsr & 0x1f`: **0x10 = User**, 0x11 FIQ, 0x12 IRQ, 0x13
Supervisor(kernel), 0x17 Abort, 0x1b Undefined, 0x1f System. Kernel addresses are 0x8000xxxx/
0xc0xxxxxx (top-half); user/dyld addresses are 0x2bxxxxxx..0x3fxxxxxx. `_nz` = count of non-zero
saved words (0 on every sample => saved-state offsets wrong, a MEASUREMENT defect).

### HYPOTHESIS A - SPINNING (user-space)
Sampled frames: `_cpsr & 0x1f == 0x10` (User) on every sample; `_pc` in the user map
(most likely **0x2be9xxxx**, i.e. dyld's runtime `__TEXT` [0x2be7c000,0x2bed4000), or the
shared region [0x2c000000,0x40000000)); `_pc` ADVANCES or REPEATS over consecutive samples.
A REPEATING user `_pc` = a tight loop; an advancing `_pc` = forward progress (not a stall).
=> The bug is in **user-space initialization in dyld**, specifically the code that follows the
caller of the -3 trio.
NEXT LOOK: dyld `ImageLoader::link` (link 0x2be09a18, size 0x28c; the -3 caller at link
0x2be09b11 = runner link+0xa9, runtime 0x2be85b11) and whatever it loops on after the 3rd
`mach_absolute_time`. Also the **commpage validity byte at 0xffff4090** (see §6): if it is 0,
`_mach_absolute_time` takes the SVC slow path on every call - check whether the commpage alias
(990-993 rung) actually publishes a valid mach_absolute_time structure. Also dyld's
hash-table/`addImagesToAllImages` symbolication state (link 0x2be08a98).

### HYPOTHESIS B - ASLEEP (kernel)
Sampled frames: `_cpsr & 0x1f != 0x10` (kernel mode, typically 0x13 Supervisor) on EVERY sample;
`_pc` in the kernel (0x8000xxxx/0xc0xxxxxx); often the SAME kernel pc repeatedly (blocked on a
wait) with the thread parked.
=> The bug is a **kernel wait that never completes** - a page-in, a lock deadline, or an IPC
timeout - i.e. the shared-cache page-in / `cs_validate_page` / `lck_mtx_sleep_deadline` path.
NEXT LOOK: `osfmk/vm/vm_fault.c` (the fault/`cs_validated` path around :2438), the page-in
(`ubc_subr.c` cs validation, `pmap_enter_options`), and `lck_mtx_sleep_deadline` /
`thread_call` (985/986's mutex/lost-wakeup class). NOTE the tension: §3 shows the kernel serves
NO page-ins in the tail, so a "blocked on a page-in" story would require the block to be
somewhere OTHER than the storage read door (e.g. waiting on a page that never arrives from a
not-yet-serviced request, or a CS-validation wait).
CAVEAT to pre-commit: a sampler that always catches the tick interrupt could also land on the
IDLE thread or the IRQ prologue; disambiguate by `_sp` (kernel stacks) and by whether `_pc`
varies vs is fixed at the fault/idle pc.

If BOTH modes appear (some samples User, some kernel) the thread is making progress through
syscalls - contradicting the "no SVCs after n=22" record, which would itself be a finding.

## 6. THE 0x2be97328 IDENTIFICATION (resolved)

**0x2be97328 IS IN /usr/lib/dyld.** runtime 0x2be97328 - slide 0x7c000 = link **0x2be1b328** =
`_mach_absolute_time` **+0x68** (symbol link 0x2be1b2c0, vmsize 0x6c) -> inside dyld `__TEXT`
[0x2be00000,0x2be21000). NOT the shared cache, NOT the gap.

By value, disassembling the real `/usr/lib/dyld` (extracted 196,576 B from
`/mnt/data/ios7-payload/v2/ios7/rootfs.hfs` IOS7MIN/usr/lib/dyld; ARMv7, dyld-324.1), the whole
function (ARM mode) is:
```
2be1b2c0: movw ip,#0x4088 ; movt ip,#0xffff     ; ip = 0xffff4088 = _COMM_PAGE + 0x88
2be1b2c8: ldrb r0,[ip,#8]                        ; read validity byte @ 0xffff4090
2be1b2cc: cmp r0,#0 ; beq 0x2be1b320
2be1b2d4: isb sy
2be1b2d8: push {r4,r5,r7,lr} ...
2be1b2e0: ldr r4,[ip] ; ldr r5,[ip,#4]           ; commpage secs/ticks (seqlock pair)
2be1b2e8: mrrc p15,0,r3,r1,c14                   ; CNTVCT
2be1b2ec: mrrc p15,0,r0,r3,c14
2be1b2f0: mrrc p15,0,r3,r2,c14
2be1b2f4: cmp r1,r2 ; bne 0x2be1b2e0             ; retry until stable  <-- SEQLOCK LOOP
...       (echo the pair, orr, bne loop)
2be1b314: adds r0,r0,r2 ; adcs r1,r1,r3
2be1b31c: pop {r4,r5,r7,pc}                       ; FAST RETURN
2be1b320: mvn ip,#2                              ; ip = -3
2be1b324: svc #0x80                               ; <-- SLOW PATH: SVC with r12 = -3
2be1b328: bx lr                                   ; <-- pc 0x2be97328 (runtime): the RETURN
```
So `_mach_absolute_time` is the STANDARD libsystem implementation: it reads a commpage
mach_absolute_time structure at `_COMM_PAGE + 0x88` (0xffff4088), validates it via the byte at
`+8` (0xffff4090), and if valid computes the 64-bit time itself (seqlock over CNTVCT+commpage);
**if the validity byte is 0 it falls through to `svc #0x80` with r12 = -3**, which is exactly
the kernel `ios7lab_timebase` path in traps_lo.s:285 -> `blx _mach_absolute_time` (kernel).

Therefore the recorded `pc = 0x2be97328` is the return address 4 bytes AFTER the `svc #0x80`
(the ARM `svc` return address convention), i.e. the call site in dyld's own image; but it
behaves as an ADDRESS of the running code because the SAME `_mach_absolute_time` was called
three times from the same dyld call site. The three are the same user `svc`.

The SIGNIFICANCE for 1003: **the -3 trap is NOT a raw mach trap; it is libsystem's commpage
FALLBACK**, taken because the commpage validity byte at **0xffff4090 is (presumably) ZERO** in
this image. That ties the frontier straight to the commpage alias rungs 990-993. In 991 the
frontier WAS `231x translation fault @_COMM_PAGE+0x90` (i.e. 0xffff4090!) - the same byte. So
the running question is: after 992/993 made the commpage alias map "the same page, user
read-only, XN" (@:4019-4020), is the mach_absolute_time structure at 0xffff4088 actually
PUBLISHED (validity byte = 1) or still 0? If it is 0, every `mach_absolute_time` call takes the
SVC path - and a user-space wait built on `mach_absolute_time` (or on `mach_wait_until` /
deadline loops) would re-enter the kernel constantly. Whether that is a SPIN or an ASLEEP
depends on the kernel's -3 handler returning correctly.

The lr trio resolves (link, ARM/Thumb-aware) to:
- lr 0x2be85a9f -> link 0x2be09a9f = `dyld::ImageLoader::link(...)` +0x37
- lr 0x2be85af1 -> link 0x2be09af1 = `dyld::ImageLoader::link(...)` +0x89
- lr 0x2be85b11 -> link 0x2be09b11 = `dyld::ImageLoader::link(...)` +0xa9
so the three mach_absolute_time calls are all inside a single `ImageLoader::link` call - dyld is
**linking an image** when it stalls, and it polls the clock between linking steps (the
`ImageLoader::link` body at link 0x2be09a9f/0x2be09af1/0x2be09b11 does `blx _mach_absolute_time`
per the disassembly at link 0x2be09a9c/0x2be09aec/0x2be09b0c).

  (libsystem commpage fallback via SVC -3) while linking an image, three times, then nothing.
