WHAT 1010c WAS FOR
------------------
1010b made the walk read the "true L1" but then faulted FS=5 OUT OF WINDOW at the L2 deref
(entry_stubs.c:2184) — the L2 table PA 0x46300000 is outside the entry image's single-span
identity window [gPhysBase, gPhysBase+mem_size) = [0x80000000, +0x1e400000). 1010c: bound
BOTH derefs to that window (fail open) and reach an out-of-window L2 via a temporary 1 MB
section (entry_mmio_section, the 911c mechanism), alias allowed on the ladder ordinals alone.

RESULT 1 — 1010c FIXED the 1010b crash.  CONFIRMED.
----------------------------------------------------
The storm runs the FULL ladder this time: `xnu_live_abt_pcn` / `_pten` / `_farn` / `_vmfn`
reach 0x00200000 (2,097,152) with no FS=5 walk fault and no early death. 1010b died at
launchd-start with 4 abort records; 1010c rides the whole ~2.1 M-abort storm to the freeze.
The 1010b defect (an unbounded L2 deref that killed the run) is gone.

RESULT 2 — the ALIAS mechanism WORKS.  CONFIRMED (once).
--------------------------------------------------------
At ladder ordinal pten=0x00000004 (pteva=0x2bd86f7c, an OUT-OF-WINDOW L2 case) the raw row is:
    xnu_live_abt_ptel1=0x46300201      (a COARSE L1 descriptor, type bits 0b01)
    xnu_live_abt_pteoow=0x00000001     (the walk saw the leaf PA out of window)
    xnu_live_abt_ptealias=0xa0000000   (the SECOND slot — VA_B)
    xnu_live_abt_ptemapok=0x00000001   (entry_mmio_section SUCCEEDED)
    xnu_live_abt_pteslot=0x00000000    (slot_before)
So the temporary section WAS installed, the alias VA recorded, and the restore ran. The
mechanism 1010c added is not the defect. (ptel2=0 even here: the aliased word was read but
did not present as a small-page leaf for THAT va — a separate point, below.)

RESULT 3 — at the STORM the walk reads the WRONG PAGE TABLE.  NEW FRONTIER.
--------------------------------------------------------------------------
The storm tail rows (pten >= 0x00000400, far=0x9a000, pc=0x2be8a1a0, fsr=0x0000080f,
abtcpsr=0x60000030 = USER, IRQ-off) are CONSTANT:
    xnu_live_abt_ptel1=0xfeedface      <-- an L1 SECTION descriptor (bits[1:0]=0b10)
    xnu_live_abt_ptel2=0x00000000
    xnu_live_abt_pteoow=0x00000000
    xnu_live_abt_ptemapok=0x00000000
    xnu_live_abt_ptealias=0x00000000
    xnu_live_abt_ptettbr=0x81a8605b
`0xfeedface & 3 == 0b10` = a SECTION, not the COARSE L1 an FS=15 (level-2 permission) fault
REQUIRES (a section gives FS=5/…, never level-2). So the walk returns early at
`(l1e & 3) != 1` (entry_stubs.c:2291) and never reaches the L2 — hence pteoow/ptemapok/
ptealias are ALL 0 at the storm: the window bound and the alias never engaged, because the
walk had already given up one level up.

WHY: **STATE OPENLY — the cause is NOT yet established.** The walk reads the L1 at the correct
BASE (`0x81a8605b & 0xffffc000 = 0x81a84000`) yet slot 0 yields `0xfeedface`. The contrast with
1010 (records/1010-press-read.txt:55) is decisive: 1010 used the WRONG base mask and read
`0x81a86000 + 0` → `ptel1=0x81bb1001` (a COARSE descriptor); 1010c uses the CORRECT base
`0x81a84000 + 0` → `ptel1=0xfeedface`. Same live TTBR0 (`0x81a8605b`), two different bases, and
the "correct" base yields the garbage. So the question is which physical L1 the abort-time TTBR0
really points at — NOT settled here.

**A PRIOR CAUSE CLAIM IN THIS RECORD WAS WRONG, AND IS RETRACTED.** An earlier draft attributed
this to `locore.s:1035-1039` (`dataabt_from_user`) switching TTBR0 to the kernel ttep under
`__ARM_USER_PROTECT__` before `bl sleh_abort`. That code is in the **4570** tree, NOT the tree
this image is built from. By value: the D13 build tree `external/xnu-hd2-darwin13/xnu` has
**ZERO** hits for `__ARM_USER_PROTECT__`/`uptw_ttb`/`kptw_ttb`; the installed handler is
`traps_lo.s:411` (`data_abort_crash_in_usermode`), which does NOT write TTBR0; and D13's
`sleh_abort` (`trap.c:451`) only READS TTBR0 for a printf. D13's `struct machine_thread`
(`thread.h:64-86`) has NO `uptw_ttb` — so "read the faulting thread's ttb" is not even available
the 4570 way. The correct reading of the cause is left to 1011's (A) cell: publish WHICH base
answered (`current_thread()→map→pmap→pm_l1_phys`, `entry_saved_state.h:102-105`), rather than
assume a mechanism. This is [[mi4-one-value-two-definitions]] in a different sense: two trees
named `locore.s`, and the citation was to the one not built.

The TTBR0-base mask 1010b fixed (0xffffc000) is NOT the issue here; the checker's stale
[A] VERDICT text blamed that mask and was re-keyed to the observable (see FOLLOW-UP).

RESULT 4 — the (B) vm_fault return IS read at the storm.  NEW, DECISIVE.
-------------------------------------------------------------------------
1010/1010b only ever read the (B) cell on the PRE-storm prefix (VAs 0xcfdbd000/0x2bdc3000/…),
never at the storm (design §1.5 / records/1010-press-read.txt). 1010c's tail rows DO carry it,
paired to the storm ordinal:
    xnu_live_abt_vmfret=0x00000000   = KERN_SUCCESS
    xnu_live_abt_vmfprot=0x00000003  = VM_PROT_READ | VM_PROT_WRITE   (a WRITE fault)
    xnu_live_abt_vmfva=0x0009a000
So: **for the user WRITE fault at far=0x9a000, `vm_fault` returns KERN_SUCCESS** — the retry
precondition is now MEASURED at the storm, not inferred. The handler's `result == KERN_SUCCESS`
arm (trap.c:571) takes `goto exception_return` and re-runs the faulting instruction: the ~2.1 M
retry, 24.4 s freeze, is the faithful consequence.

-------------------------------
* APX STILL UNREAD. The leaf (bit 9 = APX) is not in this log: the walk's L1 read returned a
  non-coarse word (`0xfeedface`), so it never reached the L2. F1a vs F1b remains UNDECIDABLE.
* THE CAUSE OF THE NON-COARSE L1 READ IS OPEN (see RESULT 3): the base mask is correct and the
  live TTBR0 is the same value 1010 saw; only the base it masks to differs. 1011's (A) cell must
  MEASURE which base answered before any fix is built on a cause.
* The DISCRIMINATOR GAP (docs/1011-discriminator-gap.md): the vm_map_entry `protection` — the
  cell that actually separates F1a (entry grants WRITE, a strip lost it) from F1b (entry denies
  WRITE) — is published by NOTHING. The (B) vm_fault return is NOT the discriminator (it reads
  KERN_SUCCESS in either case).
* The only previous "storm vmfret" claim was an INFERENCE from the pre-storm prefix
  (1010). 1010c replaces the inference with a measurement: vmfret=0 at the storm.
