(entry_stubs.c:2184) — the L2 table PA 0x46300000 is outside the entry image's single-span

RESULT 3 — at the STORM the walk reads the WRONG PAGE TABLE.  NEW FRONTIER.
--------------------------------------------------------------------------
The storm tail rows (pten >= 0x00000400, far=0x9a000, pc=0x2be8a1a0, fsr=0x0000080f,
abtcpsr=0x60000030 = USER, IRQ-off) are CONSTANT:
    xnu_live_abt_ptel1=0xfeedface      <-- an L1 SECTION descriptor (bits[1:0]=0b10)
    xnu_live_abt_ptel2=0x00000000
    xnu_live_abt_pteoow=0x00000000
    xnu_live_abt_ptemapok=0x00000000
    xnu_live_abt_ptealias=0x00000000
    xnu_live_abt_ptettbr=0x81a8605b
`0xfeedface & 3 == 0b10` = a SECTION, not the COARSE L1 an FS=15 (level-2 permission) fault
REQUIRES (a section gives FS=5/…, never level-2). So the walk returns early at
`(l1e & 3) != 1` (entry_stubs.c:2291) and never reaches the L2 — hence pteoow/ptemapok/
ptealias are ALL 0 at the storm: the window bound and the alias never engaged, because the
walk had already given up one level up.

WHY: the recorder walks TTBR0 AT ABORT TIME, and XNU has already switched TTBR0 to the
KERNEL table. `locore.s:1035-1039` (`dataabt_from_user`, `__ARM_USER_PROTECT__` = 1,
`proc_reg.h:97`):
        ldr     r3, [r9, ACT_KPTW_TTB]      // Load KERNEL ttb
        mcr     p15, 0, r3, c2, c0, 0       // Set TTBR0   <-- BEFORE bl sleh_abort
        mov     r3, #0
        mcr     p15, 0, r3, c13, c0, 1      // Set CONTEXTIDR
So `entry_note_abt_pte` (called from `__wrap_sleh_abort`) reads the KERNEL page table
(`kptw_ttb`), NOT the faulting thread's `uptw_ttb`. The user mapping for `far=0x9a000` is not
in the kernel table, so its L1 slot reads a section/garbage — the APX leaf is UNREACHABLE
this way and the walk can never read it. `entry_vectors.s:199` predicted exactly this:
"TTBR0, TTBR1 … are not in [the record]; a future step that needs the mapping state again
has to add it to the wrapper." This is a [[mi4-one-value-two-definitions]] instance: "TTBR0"
means the kernel table by the time the reader looks, the user table to the fault.

The TTBR0-base mask 1010b fixed (0xffffc000) is NOT the issue here; the checker's stale
[A] VERDICT text still blames that mask and must be corrected (see FOLLOW-UP).

RESULT 4 — the (B) vm_fault return IS read at the storm.  NEW, DECISIVE.
-------------------------------------------------------------------------
1010/1010b only ever read the (B) cell on the PRE-storm prefix (VAs 0xcfdbd000/0x2bdc3000/…),
never at the storm (design §1.5 / records/1010-press-read.txt). 1010c's tail rows DO carry it,
paired to the storm ordinal:
    xnu_live_abt_vmfret=0x00000000   = KERN_SUCCESS
    xnu_live_abt_vmfprot=0x00000003  = VM_PROT_READ | VM_PROT_WRITE   (a WRITE fault)
    xnu_live_abt_vmfva=0x0009a000
So: **for the user WRITE fault at far=0x9a000, `vm_fault` returns KERN_SUCCESS** — the retry
precondition is now MEASURED at the storm, not inferred. The handler's `result == KERN_SUCCESS`
arm (trap.c:571) takes `goto exception_return` and re-runs the faulting instruction: the ~2.1 M
retry, 24.4 s freeze, is the faithful consequence.
