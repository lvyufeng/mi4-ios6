RESULT 3 — THE (A) WALK'S TTBR0 BASE MASK IS WRONG.  1010b's "fix" WAS TO A SECOND WRONG MASK.
---------------------------------------------------------------------------------------------
1010c's frontier: the walk reads `ptel1=0xfeedface` at the storm.  `0xfeedface` is **MH_MAGIC**
(the Mach-O magic, src/stage90.h:165) — the walk is reading a Mach-O image HEADER, not an L1 table.

The mask is the defect.  `stage90_read_l2_pte` (entry_stubs.c:2263) does:

    base &= STAGE90_TTBR_BASE_MASK;     /* 0xffffc000, entry_stubs.c:2112 */

with the comment (entry_stubs.c:2107) claiming "an L1 table is L1_SIZE = 0x4000 = 16 KB aligned".
That is true only for **TTBCR.N=0**.  THIS PORT PROGRAMS N=2 (`arm_vm_init.c:475 set_mmu_ttbcr(2)`,
the walk itself reads `n = ttbcr & 7` at entry_stubs.c:2241).  With TTBCR.N=2, ARM's split is
2^(32-N)=2^30 and TTBR0's table alignment is 2^(14-N) = 2^12 = **4 KB**, so the base is bits[31:12]
=> mask **0xfffff000** (or 0xffffff00..0xffffffc0, all of which preserve bits[31:14]).

PROOF BY VALUE, FROM THIS VERY CAPTURE:
    live TTBR0                    = 0x81a8605b
    0x81a8605b & 0xffffc000       = 0x81a84000   -> the walk read MH_MAGIC  (WRONG, 8 KB low)
    0x81a8605b & 0xfffff000       = 0x81a86000   = xnu_live_abt_ptethr
                                                 = pmap->pm_l1_phys  (the (A) cell's OWN measurement)
0x81a86000 is 4 KB-aligned and NOT 16 KB-aligned — exactly what TTBCR.N=2 requires, and why
`& 0xffffc000` lands 8 KB below it in a Mach-O image.  The (A) cell's `ptethr` (the faulting thread's
own L1 base, read `current_thread()->map->pmap->pm_l1_phys`) is the INDEPENDENT witness that names
the true base: the walk should have read 0x81a86000 and used 0xfffff000 to reach it.

So the sequence of masks is:
  1010   mask 0xfffffc00 -> base 0x81a86000 (CORRECT base by luck — bits[12:10]=0) -> read 0x81bb1001
                                                       (a COARSE descriptor, correct for the odd VA)
  1010b/c/1011  mask 0xffffc000 -> base 0x81a84000 (WRONG, 8 KB low) -> read MH_MAGIC 0xfeedface
**1010b fixed one wrong mask into a second wrong mask; the base it reads has been wrong ever since,
so the L2 LEAF (APX bit 9) has never been read and F1a/F1b (the APX cell) has been UNDECIDABLE by
the walk from 1010b onward.**  The (E') cell, added in 1011, broke that deadlock from the vm_map side.

The (A) cell's comparison text ("_ptethr AGREES with _ptettbr") is an ARTIFACT: the checker masks
BOTH with 0xffffc000 (0x81a86000 -> 0x81a84000, 0x81a8605b -> 0x81a84000), so it "agrees" only
because it applies the SAME wrong mask to both — [[mi4-one-value-two-definitions]]: the raw numbers
differ (0x81a86000 vs 0x81a8605b) and the mask hides the difference that matters (bit13).
