== 1. THE DISPATCH ARITHMETIC (traps_lo.s, `fleh_swi`) ==
`EnterARM(fleh_swi)` is the SWI vector (`exctramps.s:65 .long _fleh_swi`). r11 = r12 = the user's
SVC number (traps_lo.s:177 `mov r11, r12`). Then:

  :186  cmn     r11, #3            ; r11 == -3 ?  (the only special case)
  :187  beq     ios7lab_timebase   ; -- see §5
  :190  cmp     r11, #0x80000000
  :191  beq     swi_trap           ; -- the cache/thread 0x80000000 traps
  :194  rsbs    r5, r11, #0        ; r5 = 0 - r11  (= -r11); flags set
  :195  ble     swi_unix           ; r5 <= 0 (signed) -> not a mach trap
  :197  swi_mach:
  :201  cmp     r5, #0x80          ; r5 >= 128 -> out of range
  :205  add     r11, r5, r5, lsl#1 ; r11 = r5 * 3
  :206  add     r1, r1, r11, lsl#2 ; r1 = table + r5*3*4 = table + r5*12
  :208  ldr     r1, [r1, #4]       ; r1 = entry.fn  (fn is the 2nd word of the entry)
  :209  LOAD_ADDR(r2, kern_invalid)
  :213  beq     swi_mach_error      ; entry.fn == kern_invalid -> PANIC
  :214  bx      r1                  ; else call the handler

The entry stride is confirmed BY VALUE: `mach_trap_t` is 12 bytes (`syscall_sw.h:71-78` =
`{ int mach_trap_arg_count; kern_return_t (*mach_trap_function)(void *); const char *name; }`,
3 words). `r5*12 + 4` = the fn slot of entry r5. So the **table index IS r5 = -r11.**

**For r11 = ~14 = 0xFFFFFFF1 (i.e. `mvn ip,#14`):**
    r5 = 0 - 0xFFFFFFF1 = 15         (`rsbs r5, r11, #0`)
    ble not taken (15 > 0)
    cmp r5,#0x80 -> 15 < 128, in range
    add r1, table, 15*12 ; ldr r1,[r1,#4]
**FINAL TABLE INDEX = 15.**  (Integer stated: **15**.)

**Therefore `mvn ip,#14` == index 15.** The `kernel_trap(name, -N, nargs)` macro pads 64-bit args,
which is why the *source* numbers are -10/-12/-14 (`syscall_sw.h:86-88`) but the *wire* numbers are
-11/-13/-15. Both 1019 documents quoted the source numbers; `-15` is the wire value of trap 15.

== 3. IS `svc #0x80` FROM `_mach_vm_map` ACTUALLY REACHED? (full shim, by value) ==
`_mach_vm_map` = libsystem_kernel.dylib 0x381c6618, **Thumb** (entry pic slot bit0=1, 1019 §1;
force-thumb disasm coherent). Full body:

    0x381c6618  push {r4,r5,r6,r7,lr}; add r7,sp,#12; stmdb sp!,{r8,sl,fp}; sub sp,#48
    0x381c6624  ldr r6,[r7,#12]  0x381c6628  mov fp,r0 (task) ...
    0x381c663c  ldr r0,[r7,#20]; cmp r0,#0; bne 0x381c668c        <-  GUARD, leg 1
    0x381c6640  cmp.w lr,#7   ([r7,#40]); it eq
    0x381c6646  cmpeq.w r9,#1 ([r7,#44]); bne.n 0x381c668c        <-  GUARD, legs 2 & 3
    0x381c664c  stmia.w sp,{r1,r6} ... (builds the fast-trap register frame) ...
    0x381c666a  blx 0x381c5960                                    <-  FAST TRAP
    0x381c666e..0x381c6688  restore regs; movs r0,#3; movt r0,#4096 (sentinel 0x10000003)
    0x381c6688  cmp r4,r0; bne.n 0x381c66ba                       <-  MIG fallback if != sentinel
    0x381c66b4  bl 0x381c7f74                                     <-  MIG/slow demux (libsyscall)
    0x381c66ba  movw/movt r0; add r0,pc; ldr r6,[r0]              <-  r6 = *(0x39f38086)
    0x381c66c6  cbz r6, 0x381c66e2
    0x381c66e0  blx r6                                            <-  INDIRECT HOOK (runtime ptr)
    0x381c66e2  mov r0,r4; epilogue

**YES** — the fast path reaches `blx 0x381c5960`, and 0x381c5960 (ARM) really is
`mov ip,sp; ...; mvn ip,#14; svc #0x80; ...; bx lr`, i.e. ip = 0xFFFFFFF1 = -15. So *when the fast
guard passes*, this shim issues svc with the mach-trap number **-15 == index 15.** The guard is only
for three specific low-level field values; if it fails the shim falls to `bl 0x381c7f74` (the MIG
demux on the 0x381c7f74..region, whose own body issues NO svc — only `mvn.w`/`blx` calls) and/or
`blx r6` (an indirect runtime hook, pointer at 0x39f38086). Which leg pid 1 took is UNMEASURED.

== 5. RESOLVING THE CONTRADICTION ==
* The arithmetic is settled: `mvn ip,#14` => index **15** (claim 2 right; `docs/1019-design.md` §0's
  "trap 14" and `records/1019-osalloc-extract.txt` §2's "-14" caption are BOTH off by one — they
  read the literal `14` from `mvn ip,#14` instead of computing `~14`. extract's §2 *conclusion*
  ("trap 15") is right; its *label* "-14" is wrong.)
* The two readings are NOT actually inconsistent on the dispatch; they differ on the *label* only.
* `xnu_live_usvc_num = 0xfffffffd` is **-3 = the `ios7lab_timebase` (mach_absolute_time) special
  case** — NOT mach_msg (-31), and not mach_vm_map (-15). So -3 does NOT mean "mach_vm_map is a MIG
  message"; it means the last SVC the witness recorded was a timebase call.
* Whether `svc #0x80` in the shim is on pid 1's path: the capture's usvc trace covers every svc that
  entered `fleh_swi` (the FIRST thing the vector does, before any dispatch). It shows NO -15. So on
  the observed run the -15 fast-trap svc was **not issued** — either the shim's fast guard failed and
  the call took the `bl 0x381c7f74` / `blx r6` fallback, or the frontier (`udf`) fired before any
  mach_vm_map was attempted. Which one is **UNMEASURED** (the guard's live field values were not
  recorded). If it HAD issued -15, the kern_invalid row would have panicked, and no panic is present.

== 6. VERDICT ==
The integer trap number pid 1's `mach_vm_map` call carries — **provided it takes the
libsystem_kernel fast-trap shim** (0x381c6618 -> guard passes -> blx 0x381c5960) — is **15**:
`mvn ip,#14` sets ip = 0xFFFFFFF1 = -15, `rsbs r5,r11,#0` -> 15, and the 12-byte `mach_trap_t` stride
gives fn at table+184 = 15*12+4. Claim 2 is correct by value; the "trap 14" in `docs/1019-design.md`
§0 is a misread of `mvn` (it is a bitwise NOT: ~14=15, not 14). BUT that trap number is **NOT
observed on pid 1's path**: the live capture's `xnu_live_usvc_num` shows -3 (timebase) and never -15
and never -31, and there is no panic. And `mach_trap_table[15]` in the LINKED D13 image is
`kern_invalid` **by value** (xnu_arm_entry.elf @0x8055d4b4 entry 15 = 0x80486408; the io7lab row is
not compiled in). So `mach_trap_table[15]=kern_invalid` is a REAL wall **only if** a -15 svc is
issued — which would `swi_mach_error` -> panic, which did NOT happen. Therefore either (a) the
mach_vm_map call did not go through the fast-trap svc at all (fell to the `bl 0x381c7f74` MIG demux
or the `blx r6` runtime hook), or (b) it was never reached before the `udf` loop. **UNMEASURED:**
which of (a)/(b); the exact identity of the `blx r6` hook target at 0x39f38086; whether pid 1's
specific `_mach_vm_map` call satisfied the 0x381c663c guard on that run.
