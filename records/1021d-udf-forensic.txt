1. THE INSTRUCTION, BY VALUE — it IS `udf #254`, in Thumb, and ONLY in Thumb
====================================================================================================
Bytes at the frontier (python read of the cache, fileoff = va - 0x2c000000):
    0x3823aa54: fe de 46 c0   (0x3823aa56 = c046 = nop)
Read FOUR independent ways (all CONFIRMED):
  (a) Thumb-16 @ 0x3823aa54, `objdump -M force-thumb` on bytes `fe de`:
        defe  udf #254 ; 0xfe
  (b) Thumb word is halfwords `defe c046` = `udf #254; nop` — a 4-byte-aligned trap+nop, i.e. the
      compiler's `__builtin_trap()`-shaped idiom (trap + pad so the next symbol stays aligned).
  (c) ARM-word read of the same 4 bytes `fe de 46 c0` = 0xc046defe = `strdgt sp,[r6],#-238`. That is
      NOT a valid `udf` and NOT a sensible instruction; but the CPU is in Thumb (the run's
      `cpsr = 0x20000030`, T bit (0x20) SET — capture :4120), so the ARM reading never applies.
  (d) ARM `udf` would need encoding `0xe7f0??f0`..; the byte pair here is `fe de`, so the SAME
      physical halfword is `udf #254` only in the Thumb decode. There is no ARM-encoded `udf` here.
So the encoding is unconditionally a Thumb `udf #254`. CONFIRMED.

3. WHAT XNU's HANDLER DOES WITH A USER-MODE `udf` (CONFIRMED against the tree AND against the
   RAISE arm that actually ran)
====================================================================================================
`external/xnu-hd2-darwin13/xnu/osfmk/arm/trap.c` `sleh_undef`:
  :1094-1102  user-mode only sets `thumb_offset = (cpsr & (1<<5)) ? 1 : 0` (T bit), then `copyin`

              encoding test; the source comment says so out loud ("Check the instruction encoding to
              see if it's a coprocessor instruction" ... "dyld's faulting one ... I really just need
              to redo all of the VFP detection code").
  :1108-1126   INTO that branch:  `thread->machine.vfp_dirty = 0;`
              * with `STAGE90_XNU_UNDEF_RAISE` OFF (1019's arm):
                    if `!thread->machine.vfp_enable` -> `vfp_enable_exception(TRUE);
                    vfp_context_load(...); vfp_enable=TRUE;` then `return;` — **and this return is
                    UNCONDITIONAL: vfp_enable is set but the PC never advances, so the SAME `udf`
                    re-executes** -> the 1018/1019 sweep (trap->enable->return->re-trap) is the loop.
              * with `STAGE90_XNU_UNDEF_RAISE` ON (the arm that ran, 1020b):

                    `/* else FALL THROUGH */`

**The "false positive" carve-out does NOT cover `0xdefe` (CONFIRMED, and this is the crux why the
raise is CORRECT for our case).**
  * Apple's *general* ARM kernel (`external/xnu-4570.1.46/osfmk/arm/trap.c:118-240`) does NOT enable
    FP lazily at all: it computes `exception = EXC_BAD_INSTRUCTION` and classifies with
    `IS_THUMB_VFP(instr32)` / `IS_ARM_VFP(instr)`, and where it does special-case a user instruction
    it is the **dtrace fast-trap**, `FASTTRAP_THUMB_INSTR`, defined at
    `external/xnu-4570.1.46/osfmk/arm/trap.c:78-79` as `0xdefc` (`udf #252`) / `0xe7ffdefc`.

    dtrace fast-trap marker; it is a bare `udf #254`. The "Apple's real ARM kernel treats the
    coprocessor/VFP-not-enabled case by enabling FP and returning" reading is TRUE for *VFP-encoded*
    undefined instructions, and REFUTED for `0xdefe`.
  * The 1020b run is the by-value witness for the carve-out NOT firing: the raise happened
    (capture :4115). If `0xdefe` had been treated as VFP/NEON, the arm would have returned and the
    `_seq` would have climbed indefinitely, as it did in 1019's run. It did not (the sequence
    stopped at 2). CONFIRMED.

6. WHAT "CORRECT HANDLING" WOULD MEAN — and why raising is still right for `0xdefe`
====================================================================================================
Could `0xdefe` be a mis-decoded or DELIBERATE encoding that libsystem uses to signal "shared cache
resolver stub / mmap failed hard"? Read for a benign reading of each:
  (i) "shared-cache resolver stub / patched branch island" — a resolver stub is an out-of-line island
      that is *jumped to* and patched, i.e. a **success** control-flow device. REFUTED: §2 shows
      `0x3823aa54` is reached ONLY by `mach_vm_map != 0` failure branches and carries a bare
      `udf #254; nop` with no island/dispatch marker. A resolver stub would not sit behind a
      `cmp r0,#0 / bne` on the mmap return.
  (ii) "dtrace / GDB trap" — REFUTED by the encoding: `FASTTRAP_THUMB_INSTR = 0xdefc` (udf #252),
      `IS_THUMB_GDB_TRAP` likewise distinct; `0xdefe` matches neither.
  (iii) "VFP/NEON false positive the handler should absorb" — REFUTED: `0xdefe` is a Thumb `udf`,
      not a VFP encoding; the `0xfedeffe7` stand-in in our tree is the analogous *ARM* deliberate
      `udf`, and the tree already treats THAT as a raise. Our arm's measured behaviour (raise once,
      stop) is the correct analogue.
Conclusion: the ONLY reading left is the compiler's fatal-trap stub on the allocator's
mmap-failure path. Raising `EXC_BAD_INSTRUCTION` is the correct response. CONFIRMED.

**Does raising leave pid 1 dead? YES.** `external/xnu-hd2-darwin13/xnu/osfmk/kern/exception.c:322-349`
(`thread_exception_deliver` -> `exception_deliver`): if delivery is not `KERN_SUCCESS` /
`MACH_RCV_PORT_DIED`, "Nobody handled it, **terminate the task**" -> `task_terminate(task)`. At this
point in iOS bring-up pid 1 (launchd) has installed NO `EXC_BAD_INSTRUCTION` handler (there is no
dyld/libsystem in the run to install one — this is the very first userspace code, and 1020b's own
console is inside the *loading* of libsystem_platform). So the task terminates; for pid 1 that is
`panic("init died")`. launchd does not continue. The raise is faithful — it is not a solution.

**Is the NEON fix (1021/1021c) sufficient to boot iOS? NO.** The 1021 root cause (FPEXC.EN
save-without-restore) is real and must be fixed, but it is DOWNSTREAM of this: after the NEON fix,
if pid 1's allocator mmap could succeed, the `udf` would not trip. It cannot succeed, because trap 15
is `kern_invalid`. So the boot-blocking work is: **(a) install mach trap 15** (turn the
`IOS7_COMPAT_PLATFORM` gate ON, or add the tree's `ios7lab_mach_vm_map_trap` row unconditionally),
and **(b)** fix the FPEXC.EN restore. (a) alone unblocks the `udf`; (b) alone does not. Both are owed.

9.2 RE-DERIVATION -- the shim's `r7`, byte by byte (CONFIRMS the parent; guard-leg §1 was WRONG)
  Shim prologue, re-carved from the cache at VA 0x381c6618 (bytes: `f0 b5 03 af 2d e9 00 0d 8c b0`),
  disassembled `-M force-thumb`:
      0x381c6618: b5f0        push  {r4,r5,r6,r7,lr}   ; FIVE words = 20 bytes
      0x381c661a: af03        add   r7, sp, #12
      0x381c661c: e92d 0d00   stmdb sp!, {r8,sl,fp}    ; happens AFTER the add

  Arithmetic (sp here = the value on entry, i.e. the caller's sp):
      after `push {r4,r5,r6,r7,lr}`   sp = caller_sp - 20
      after `add r7, sp, #12`         r7 = (caller_sp - 20) + 12 = **caller_sp - 8**

  `r7 = caller_sp`.  That is **WRONG**: the 3-word `stmdb {r8,sl,fp}` executes AFTER `add r7`, so it
  cannot cancel it; the `push {r4,r5,r6,r7,lr}` it should have counted is FIVE words.  I do not need
  to trust either arithmetic -- the shim's own epilogue shows the idiom: at 0x381c66e4
  `add sp,#48; ldmia.w sp!,{r8,sl,fp}` (cancelling `sub sp,#48` and the 3-word stmdb), then
  0x381c66ea `pop {r4,r5,r6,r7,pc}` pops exactly the FIVE words the five-word prologue pushed.
  Consistent with five, not three.
