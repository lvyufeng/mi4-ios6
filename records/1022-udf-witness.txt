1022 — THE udf WITNESS: pid 1's `__os_alloc_slow` udf WAS RAISED (by value)
=================================================================================
Author: lead. Read-only (this file is the only write). No build/press/device.

WHY THIS RECORD. records/1021d-mmap-failure.txt §B.3 and records/1021d-udf-forensic.txt §9 left
the SAME caveat open: no capture had witnessed a USER-mode `udf` at the `__os_alloc_slow`
site, so "the failing call takes the fast trap leg" could not be tied to a live event. It can,
partly.

WHAT THIS SETTLES  =>  the udf at pid 1's mach_vm_map-failure site IS REAL, IS TAKEN, and IS RAISED.
  pid 1's `__os_alloc_slow` really does fail its map, and the run dies there (the udf is a genuine
  fatal trap on the allocator's failure path -- records/1021d-udf-forensic.txt §1, now live).

WHAT THIS DOES **NOT** SETTLE (state it plainly, do not paper over)
---------------------------------------------------------------------------------
The udf is reached from EITHER failure branch (CALL1 @0x3823a9b0 `bne`, CALL2 @0x3823aa26). Both call
the SAME shim `blx 0x3823e6e4`, so the pc does NOT say which one fired, hence NOT whether the failing
call took the fast trap leg (a) or the slow leg (b). The trap-15 fix is decisive ONLY for leg (a).
records/1021d-mmap-failure.txt §B.3 residue (i)/(ii) therefore REMAINS OPEN.

To close it in one run, the next rung must record at the udf WHICH site led there (lr = 0x3823a9af
for site (a) vs 0x3823aa23 for site (b)), and/or the live r12 at the shim's `svc` (or fleh_swi's r11)
to tokenise the trap number rather than infer it.

BOTTOM LINE FOR 1022. The blocker is a port defect (`mach_trap_table[15] = kern_invalid`) sitting
directly on a LIVE user path: pid 1 is observed to die at `__os_alloc_slow+0x108` because its
mach_vm_map failed. Installing the trap-15 row is warranted regardless of the leg question.
